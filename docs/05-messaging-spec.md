# 메시지와 보관

> 상태: 확정 · 최종 수정 2026-09-19

## 1. 메시지란 무엇인가

한 사람이 특정 시각에 상대에게 보낸 한 덩어리의 내용이다. 한 번 보내면 내용은 바뀌지 않는다. 바뀌는 건 **어디까지 갔는지**뿐이다.

```
Message
├─ id           ULID. 전 세계에서 겹치지 않는 값
├─ author       누가 보냈나
├─ content      무엇을 보냈나
├─ sentAt       언제 보냈나 (보낸 기기 시각)
├─ receivedAt   언제 받았나 (받은 기기 시각, 내가 보낸 것이면 없음)
├─ seq          보낸 사람 기준 순번
└─ delivery     어디까지 갔나
```

### 왜 ULID인가

시각이 앞에 들어간 식별자라 **정렬하면 시간순이 된다.** 두 기기가 각자 만들어도 겹치지 않는다. 그래서 내보낸 파일을 합칠 때 같은 메시지인지 판단하는 기준으로 쓸 수 있고, 동시에 순서도 알려준다.

### 왜 시각이 두 개인가

두 폰의 시계가 다를 수 있다. 특히 시차를 넘는 비행에서는 한쪽이 먼저 시간대를 바꿀 수 있다.

- 화면에 보여줄 때는 **받은 시각**을 기준으로 줄 세운다. 내 기기에서 본 순서가 흐트러지지 않는다.
- 보낸 시각은 같이 저장해두고, 두 시각이 크게 어긋나면 화면에 작게 표시한다.

## 2. 보낼 수 있는 것

```
MessageContent
├─ Text        글자. 최대 4000자
├─ Doodle      낙서. 선의 좌표 묶음
├─ Nudge       콕 찌르기. 내용 없음
├─ Photo       사진
├─ Voice       음성 메시지
├─ Sticker     캐릭터 이모티콘
└─ System      앱이 끼워 넣는 알림 ("연결이 끊겼어요" 등)
```

낙서를 그림 파일이 아니라 **선의 좌표로** 저장하는 이유가 있다. 크기가 훨씬 작아서 블루투스로도 나를 수 있고, 화면 크기가 달라도 선명하게 다시 그릴 수 있다.

```ts
Doodle = {
  strokes: Array<{
    points: Array<[x: number, y: number]>   // 0~1 사이 비율 좌표
    color: string                            // 토큰 이름. 실제 색이 아님
    width: number
  }>
}
```

색을 `#FF0000` 대신 토큰 이름으로 저장하는 이유는, 어두운 화면과 밝은 화면에서 각각 알맞은 색으로 나오게 하기 위해서다.

### 사진

사진은 다른 내용과 달리 **봉투 안에 담기지 않는다.** 너무 크기 때문이다. 메시지에는 사진에 대한 설명만 넣고, 실제 그림은 따로 나른다.

```ts
Photo = {
  assetId: string      // 이 사진의 고유 번호. 조각들을 이 번호로 찾는다
  width: number
  height: number
  byteLength: number
  preview?: string     // 아주 작게(32px) 줄인 그림. base64 로 4000자 안
  caption?: string     // 곁들이는 말. 200자 안
}
```

> 2026-09-19 에 코드(`domain/message/MessageContent.ts`)에 맞췄다. 계획에 있던
> `blurHash` 대신 **32px 로 줄인 진짜 그림**을 `preview` 로 싣는다. 몇백 바이트라
> 메시지와 같이 가고, blurHash 라이브러리를 하나 덜 들인다. `localUri` 는 없다.
> 파일 위치는 `assetId` 로 셈한다(`assets/<assetId>.jpg`).

`preview` 가 중요하다. **사진이 다 오기 전에 흐릿한 모습을 먼저 보여줄 수 있다.** 받는 동안 빈 네모를 보고 있지 않아도 된다.

사진을 나르는 절차:

```
보내는 쪽                              받는 쪽
   │                                      │
   │─ message { photo, assetId, preview } ▶│  먼저 메시지가 간다
   │                                      │  → 흐릿한 미리보기가 즉시 뜨고
   │                                      │    이 assetId 의 조각을 기다리기 시작한다
   │─ asset_chunk { assetId, 번호, 내용 } ─▶│  (여러 번, 곧바로 이어서)
   │─ asset_chunk ... ────────────────────▶│
   │                                      │  마지막 조각이 오면 파일로 합친다
   │                                      │
   ─ ─ ─ 끊겼다가 다시 붙으면 ─ ─ ─ ─ ─ ─ ─ ─
   │◀─ asset_request { assetId, missing } ─│  인사 뒤에 못 받은 조각만 달라고 한다
   │─ asset_chunk (그것만) ───────────────▶│
```

> 2026-09-19 에 바꿨다. 계획에 있던 `asset_offer` 와 `asset_complete` 는 **만들지
> 않았다.** 메시지 자체에 크기(`byteLength`)가 실리므로 따로 알릴 것이 없고, 조각
> 수는 크기로 셈한다. 검증값도 없다. 조각마다 번호가 있어 빠지면 채우고, 두 사람만
> 쓰는 길이라 바뀌어 올 일이 없다.

- 한 조각은 48 KB(`CHUNK_BYTES`)다. base64 로 실으면 64 KB 다. 한 파일은 8 MB(`MAX_ASSET_BYTES`)까지.
- **받는 쪽은 메시지를 불러올 때 조각을 기다리기 시작한다**(`trackAssets`). 사진·음성 메시지마다 파일이 있는지 보고, 없으면 `expect` 로 판을 깐다. 이걸 안 하면 조각이 와도 "모르는 사진" 으로 버려져 영영 "기다리는 중" 이다(2026-09-19 실제로 그랬다). 앱을 껐다 켜도 마찬가지라 불러올 때마다 본다.
  - 내 것인데 파일이 없으면 보내다 죽은 것이다. 상대에게 달라고 할 수 없어 건너뛴다.
  - **12시간(`TRACK_ASSETS_WITHIN_MS`)보다 오래된 것은 안 기다린다.** 며칠 전 시험하다 만 사진까지 인사할 때마다 달라고 하면 좁은 길이 그것으로 꽉 차서 지금 대화가 밀린다. 한 비행 안의 것만 챙긴다.
- 받는 쪽이 어디까지 받았는지 알고 있어서, 끊겼다 붙으면 인사 뒤에 **못 받은 조각만** 다시 요청한다(`asset_request`). 처음부터 다시 받지 않는다.
- 모르는 `assetId` 의 조각이 오면 버리되 연결은 그대로 둔다.
- 사진은 앱 폴더의 `assets/` 아래에 `<assetId>.jpg` 로 저장한다. 음성도 같은 곳에 같은 이름 규칙으로 둔다(확장자가 `.jpg` 라도 내용은 m4a 다. 재생할 때 사정은 음성 메시지 항목).
- 보내는 쪽도 줄인 사진을 같은 곳에 저장한다. 내가 보낸 사진도 나중에 다시 봐야 하기 때문이다.
- **블루투스로도 보낸다.** 2026-09-19 에 바꿨다. 그전에는 대기 줄에 두고 Wi-Fi 가 열리면 내보냈는데, 비행기에서는 Wi-Fi 가 영영 안 열린다(04 문서 1.1).

#### 크기를 고른다

보내기 전에 **얼마나 줄일지** 고르고, 좁은 길이면 **얼마나 걸릴지** 보여준다.

| 고름 | 긴 변 | JPEG 화질 | 대략 크기 | 블루투스로 (초당 3KB) |
|---|---|---|---|---|
| 작게 (`small`) | 800px | 0.5 | 80 KB | 약 30초 |
| 중간 (`medium`, 기본) | 1600px | 0.8 | 350 KB | 약 2분 |
| 원본 (`original`) | 4096px | 0.9 | 3 MB | 약 17분 |

(`application/assets/AssetChunks.ts` 의 `PHOTO_SIZES`, `NARROW_BYTES_PER_SECOND`)

시간은 어림이다. 실제로는 연결 간격에 따라 두세 배 달라진다. 그래도 "약 2분" 과
"약 17분" 을 보고 고르는 것과 모른 채 기다리는 것은 다르다.

#### 얼마나 갔나

조각이 하나 갈 때마다 진행률을 올린다(`onProgress`). 좁은 길에서는 한 조각(48KB)이
몇십 초 걸리므로 **조각 안에서도** 블루투스 쪽 부분(185바이트) 단위로 소수를 올린다.
안 그러면 30초 동안 막대가 안 움직여 멈춘 줄 안다. 받는 쪽도 같은 방식으로 그린다(`onReceiveProgress`).

### 이모티콘

```ts
Sticker = {
  character: CharacterId    // 어느 캐릭터인지
  pose: StickerPose         // 아래 스물아홉 가지
}
```

그림을 나르지 않는다. **어떤 캐릭터가 어떤 자세인지**만 보내면 받는 쪽이 코드로 그린다. 그래서 몇십 바이트면 충분하고 블루투스로도 즉시 간다.

#### 무엇을 넣었나

세 시간 동안 말을 못 한다. 옆자리에 앉아 있어도 소리를 낼 수 없으니 하고 싶은 말이 다 글이 된다. **자주 하게 되는 말은 그림이 글보다 빠르고 오해도 적다.**

| 묶음 | 자세 |
|---|---|
| 건네는 말 | `wave` `thumbsUp` `heart` `miss` `laugh` `wink` `shy` `excited` `please` `clap` |
| 기분 | `think` `surprised` `no` `angry` `stuffy` `loud` `scared` `cry` `sorry` `bored` |
| 몸 | `sleep` `stiff` `cold` `hot` `toilet` `eat` `hungry` `yummy` `full` |

고르는 칸에 **두 줄로** 놓고 옆으로 민다. 한 줄에 네댓 개가 보이니 두어 번 밀면 끝이다.

**길게 누르면 무슨 말인지 뜬다.** 그림만으로는 애매한 것이 있다 — 팔짱 낀 건 "안 돼"인지 "추워"인지, 손을 든 건 인사인지 화장실인지 헷갈린다. 짧게 누르면 그대로 나가므로 보내는 데 한 걸음이 늘지는 않는다.

뜻은 자세 이름이 아니라 **하고 싶은 말**로 적는다. "손 흔들기"가 아니라 "안녕"이다. 고르는 사람은 하고 싶은 말을 찾지 자세 이름을 찾지 않는다. (`presentation/copy/stickers.ts`)

**대화에 뜬 이모티콘도 길게 누르면 뜻이 뜬다.** 받은 쪽도 헷갈리기는 마찬가지다.
뜻은 말풍선 **옆 빈자리**에 띄운다(내 것이면 왼쪽, 상대 것이면 오른쪽). 아래에 끼워
넣으면 목록이 밀려 스크롤이 움직이고 손가락에 가렸다(2026-09-19).

**이 목록을 줄이지 않는다.** 예전 대화에 담긴 자세가 사라지면 그 말풍선을 못 그린다. 상대가 모르는 자세를 보내면 봉투 검사에서 걸러져 그 한 통만 조용히 버려진다 — 대화가 끊기지는 않는다.

#### 무엇을 그릴지는 한 곳에서 정한다

`presentation/characters/poses.ts` 가 자세마다 눈·눈썹·입·손·주변 표시를 정하고, `Sticker.tsx` 는 그 말대로 선만 긋는다. 나눠둔 덕에 두 가지가 생긴다.

- **시험할 수 있다** — 팔이 몸에서 떨어지지 않는지, 손이 눈을 가리지 않는지, 두 자세가 똑같이 생기지 않았는지를 좌표로 확인한다
- **브라우저 데모가 같은 것을 쓴다** — 데모는 `react-native-svg` 를 못 쓰지만 `poses.ts` 는 순수 TypeScript 라 그대로 가져다 쓴다. 자세를 하나 더하면 데모에도 저절로 생긴다

그림에서 지키는 것 셋.

- 팔은 **어깨나 가슴에서 시작한다.** 손만 허공에 띄우지 않는다
- 몸 앞으로 오는 팔에는 **윤곽을 두른다.** 팔과 몸이 같은 옷 색이라 겹치면 팔이 통째로 사라진다
- 손에는 **늘 테두리를 두른다.** 살색 손이 살색 얼굴 위에 오면 묻힌다

### 음성 메시지

```ts
Voice = {
  assetId: string      // 조각들을 이 번호로 찾는다
  durationMs: number   // 얼마나 긴 말인가
  byteLength: number
}
```

**떨어져 앉아도 목소리를 들려줄 수 있다.** 통화와 다른 점은 상대가 지금 듣고 있지 않아도 된다는 것이다. 자고 있으면 나중에 들으면 되고, 끊겨 있어도 보내둘 수 있다. 세 시간 비행에서는 이쪽이 더 자주 쓰인다.

사진과 **같은 길로 나른다.** `ChunkSender` 는 무엇인지 묻지 않고 `assetId` 로 바이트만 옮긴다.

```
녹음 → 기기에 두기 → 메시지 저장 → 메시지 보내기 → 조각 보내기
```

**메시지가 먼저 간다.** 그래야 상대 화면에 "15초짜리 음성" 이 바로 뜬다. `durationMs` 를 메시지에 같이 싣는 이유가 이것이다. 조각을 다 보낸 뒤에 메시지를 보내면 그동안 상대는 아무것도 모른 채 기다린다.

| | 값 | 왜 |
|---|---|---|
| 가장 긴 녹음 | **20초** | 블루투스로 10초에 40KB, 20초면 80KB 라 30초쯤 걸린다. 더 길면 그동안 글이 밀린다 |
| 가장 짧은 녹음 | 0.5초 | 그보다 짧으면 잘못 누른 것이다 |
| 음질 | 한 채널 22.05kHz, 32kbps, `.m4a`(AAC) | 말소리라 높은 음질이 필요 없다. 10초에 40KB쯤 |
| 좁은 길(블루투스) | **보낸다** | 20초에 80KB 라 견딜 만하다. 보내기 전에 걸리는 시간을 적는다 |

> 2026-09-19 에 바꿨다. 가장 긴 녹음을 60초에서 20초로, 좁은 길에서 "안 보낸다" 를
> "보낸다" 로. 비행기에서는 좁은 길뿐이라 안 보내면 이 기능이 없는 것과 같다.
> 도메인(`MAX_VOICE_MS` 60초)과 봉투 형식(2분)은 옛 앱이 보낸 긴 것도 받아주려고
> 그대로 두었다. 20초는 **녹음 창이 멈추는 길이**다(`useChatStore` 의 `MAX_VOICE_MS`).

#### 녹음 창

**한 번 눌러 시작하고, 다시 눌러 끝낸다.** 녹음 창(`VoiceRecordSheet`, 기존 `Sheet`)이 뜨고
거기서 다 한다.

1. 마이크 단추를 누르면 녹음이 시작된다(짧게 떨린다). "녹음 중 · N초" 가 오른다
2. 다시 누르면 끝난다. **20초가 되면 저절로 끝난다**
3. 길이와 크기, 블루투스면 "약 N초 걸려요" 를 보여주고 **보내기 / 버리기** 를 고른다

> 2026-09-19 에 바꿨다. 그전 계획은 "꾹 누르는 동안만 녹음" 이었다. 무전기처럼
> 누르고 있는 방식은 **눌렀는지 안 눌렀는지 알 수 없어** 놓친 줄 모르고 말을 했다.
> "켜둔 줄 모르고 엉뚱한 소리가 건너간다" 는 걱정은 20초 자동 종료와 보내기 전
> 확인으로 막는다.

녹음하는 동안에도 `mixWithOthers` 라 상대 음악은 안 끊긴다. 마치면 마이크를 놓아준다 — 잡고 있으면 음악이 계속 눌린 채로 남는다.

#### 받은 것을 들을 때

파일은 사진과 같은 곳에 `<assetId>.jpg` 로 놓인다(자원 저장소가 종류를 모른다).
iOS 재생기는 확장자로 형식을 짚어서 `.jpg` 면 소리를 안 낸다. 그래서 **틀기 전에
`.m4a` 로 복사해 그것을 튼다**(`withAudioExtension`). 2026-09-19 에 받은 음성이
안 들리던 것을 이렇게 고쳤다.

#### 오면 바로 들려주기

**이게 켜지면 사실상 무전기가 된다.** 상대가 말하면 내 이어폰에서 바로 나오고, 나는 녹음 창을 열어 답한다. 통화와 달리 둘 다 동시에 붙어 있을 필요가 없어서, 한쪽이 잠깐 끊겨도 말이 사라지지 않는다. 설정의 "오면 바로 들려주기" 로 켠다.

지키는 것 다섯. (`presentation/stores/voiceAutoplay.ts`)

| 규칙 | 왜 |
|---|---|
| 내가 보낸 것은 안 튼다 | 방금 내가 말한 것이다 |
| 한 번 튼 것은 다시 안 튼다 | 눌러서 튼 것도 똑같이 적어둔다 |
| 켠 뒤에 온 것만 튼다 | 안 그러면 켜는 순간 예전 음성이 줄줄이 재생된다 |
| 하나씩, 온 순서대로 | 두 개가 겹치면 둘 다 못 알아듣는다 |
| 앱을 보고 있을 때만 | 잠금 화면에서 소리가 나면 옆자리 승객이 듣는다 |

"켠 뒤에 온 것만" 은 **껐다 다시 켤 때도 적용된다.** 꺼둔 동안 온 것까지 몰아서 틀면 안 된다. 켜지는 순간 지금 있는 것을 전부 "이미 튼 것" 으로 친다.

다음 것이 이어지려면 **다 들었다는 신호**가 필요하다. `didJustFinish` 를 놓치면 "지금 나오는 중" 으로 남아서 한 번에 멎는다.

### 반응 (2단계 — 아직 없다)

**만들지 않았다.** 봉투 형식에도 `reaction` 이 없고 표도 없다(2026-09-19 기준).
계획만 남긴다.

메시지에 이모지를 붙이는 것이다. 새 메시지가 아니라 **기존 메시지에 딸린 표시**다.

```sql
CREATE TABLE reactions (
  message_id  TEXT NOT NULL,
  peer_id     TEXT NOT NULL,
  emoji       TEXT NOT NULL,
  created_at  INTEGER NOT NULL,
  PRIMARY KEY (message_id, peer_id)
);
```

한 사람이 한 메시지에 붙이는 반응은 하나다. 새로 붙이면 이전 것이 바뀐다. 그래서 늦게 도착한 반응이 순서가 뒤바뀌어도 시각을 비교해 최신 것만 남긴다.

## 3. 어디까지 갔나

```
  작성됨 ──▶ 보내는 중 ──▶ 전달됨 ──▶ 읽음
    │            │
    │            ▼
    └────────▶ 대기 중 ──▶ (연결되면 다시 보내는 중)
                 │
                 ▼
               실패
```

규칙:

- **뒤로 못 간다.** 읽음이 된 메시지가 전달됨으로 돌아가지 않는다. 늦게 도착한 옛 신호가 화면을 흔드는 걸 막는다.
- **실패에서는 다시 시작할 수 있다.** 사용자가 다시 보내기를 누르면 대기 중으로 돌아간다.
- 이 규칙은 `DeliveryState`가 직접 강제한다. 잘못된 전이를 요청하면 값이 바뀌지 않고 실패를 돌려준다.

### 대기 중인 메시지 내보내기

연결이 끊긴 동안 보낸 메시지는 **순번 순서 그대로** 쌓인다. 다시 붙으면 쌓인 순서대로 내보낸다. 순서가 뒤바뀌면 대화가 이상해지기 때문이다.

한 메시지는 최대 5번까지 다시 보낸다. 그래도 안 되면 실패로 두고 화면에 다시 보내기 버튼을 띄운다.

## 4. 대화

메시지를 모아둔 것이 대화(Conversation)다. 두 사람이 쓰므로 대화는 하나뿐이다.

대화가 책임지는 일:

- 메시지를 받아들일지 판단한다. 이미 있는 id면 거절한다.
- 순번의 빈틈을 찾아낸다. "3, 4, 6이 왔으니 5가 없다"를 알려준다.
- 읽지 않은 개수를 센다.

메시지가 수만 개가 되어도 문제없도록, 대화 객체가 **전부를 메모리에 안고 있지 않는다.** 화면에 보이는 구간만 데이터베이스에서 꺼내 쓴다.

### 대화 비우기는 감추기다

설정의 "대화 비우기" 는 **아무것도 지우지 않는다.** 누른 시각을 `hideMessagesBefore`
에 적어두고, 화면이 그 앞의 말을 안 그릴 뿐이다. 내보내기에는 그대로 나온다.

지우지 않는 이유: 이 앱은 메시지를 지우거나 못 읽게 만드는 변경을 하지 않는다
(CLAUDE.md "대화가 앱보다 오래 산다"). 비행기에서 잘못 눌러 세 시간의 대화를
날리는 것이 가장 나쁘다. 2026-09-19 에 넣었다.

감춘 지점까지 내려갔으면 더 불러오지 않는다.

### 화면에서 시각을 어디에 적나

한 사람이 연달아 말하면 매번 시각을 적지 않는다. 그렇다고 맨 마지막에만 적으면
5분 전 말과 방금 말이 같은 시각처럼 보인다. 그래서 **같은 사람이 같은 분(分) 안에
이어서 말한 묶음의 마지막에만** 적는다. 분이 바뀌면 그 앞 말에도 적힌다
(`presentation/components/chat/timeMarks.ts`). 날이 바뀌는 자리에는 날짜 줄을 따로
끼운다. 목록은 뒤집어 그린다(가장 새 말이 0번, 화면 아래). 그래야 키보드나 도구 줄로
목록 키가 바뀌어도 보던 아래쪽이 그대로 따라온다.

## 5. 저장

### 표 구조

```sql
CREATE TABLE messages (
  id            TEXT PRIMARY KEY,           -- ULID
  author_id     TEXT NOT NULL,
  content_kind  TEXT NOT NULL,              -- text | doodle | sticker | photo | voice | nudge | system
  content_body  TEXT NOT NULL,              -- JSON
  sent_at       INTEGER NOT NULL,           -- 밀리초
  received_at   INTEGER,
  seq           INTEGER NOT NULL,
  delivery      TEXT NOT NULL,
  link_kind     TEXT,                       -- 어느 길로 왔나 (wifi | ble | web)
  UNIQUE (author_id, seq)
);

CREATE INDEX idx_messages_received_at ON messages (received_at DESC, id DESC);
CREATE INDEX idx_messages_delivery ON messages (delivery) WHERE delivery IN ('pending','failed');
```

두 가지를 데이터베이스가 직접 막는다.

- `PRIMARY KEY (id)` — 같은 메시지가 두 번 들어가지 않는다.
- `UNIQUE (author_id, seq)` — 한 사람의 같은 순번이 두 개일 수 없다.

코드에서 실수해도 저장소가 걸러낸다.

사진·음성의 바이트는 이 표에 없다. `content_body` 에는 `assetId` 와 크기만 있고
파일은 앱 폴더 `assets/` 에 따로 둔다(2장). 그래서 파일이 없어도 말풍선은 남는다.

### 화면에 꺼내는 법

최신부터 50개씩 꺼낸다. 위로 올리면 더 꺼낸다.

`OFFSET`을 쓰지 않는다. 메시지가 쌓이면 뒤로 갈수록 느려지기 때문이다. 대신 **마지막으로 본 지점을 기준으로** 그 앞을 찾는다.

```sql
SELECT * FROM messages
WHERE (received_at, id) < (?, ?)
ORDER BY received_at DESC, id DESC
LIMIT 50;
```

## 6. 보관과 내보내기

> 제품 명세 F2-1에 대응한다. 아이폰 앱이 7일마다 만료되므로 이건 필수 기능이다.

### 6.1 세 가지 형식

| 형식 | 확장자 | 무엇에 쓰나 | 되돌릴 수 있나 |
|---|---|---|---|
| 보관 파일 | `.skywalkie.json` | 다른 기기로 옮기거나 재설치 후 되돌리기 | **가능** |
| 읽는 문서 | `.html` | 앱 없이 그냥 열어보기. 낙서까지 보인다 | 불가 |
| 글자만 | `.txt` | 어디서든 열리는 가장 단순한 형태 | 불가 |

한 번 내보낼 때 **세 개를 다 만든다.** 사용자가 고르게 하면 잘못 고를 수 있다.

### 6.2 보관 파일의 생김새

```jsonc
{
  "format": "skywalkie-archive",
  "version": 1,
  "exportedAt": 1758000000000,
  "people": [                       // 두 사람 다 담는다
    { "peerId": "...", "displayName": "...", "character": "..." },
    { "peerId": "...", "displayName": "...", "character": "..." }
  ],
  "messages": [ /* ... */ ],
  "integrity": {                    // 맨 끝에 온다
    "messageCount": 1523,
    "checksum": "sha256:...",       // 메시지 id를 정렬해 이은 값의 해시
    "firstMessageId": "01J...",
    "lastMessageId": "01J...",
    "sourceCount": 1523             // 꺼내기 시작할 때 저장소가 답한 수
  }
}
```

**두 사람을 다 담는다.** 내 것만 담으면 상대 이름과 캐릭터가 사라져서, 나중에
파일을 열었을 때 누가 한 말인지 알 수 없다.

**`integrity`가 맨 끝에 온다.** 흘려가며 쓰는 것과 검증값을 앞에 두는 것은 같이
할 수 없다. 다 읽어봐야 나오는 값이기 때문이다. JSON 은 자리 순서를 따지지 않는다.

### 검증값이 두 겹인 이유

`checksum`은 **파일이 옮겨지다 망가진 것**을 잡는다. 되돌릴 때 다시 계산해 대조한다.

`sourceCount`는 **꺼내다 만 것**을 잡는다. 이건 `checksum`으로는 못 잡는다.
저장소가 중간에 한 건을 해석하지 못하면 거기서 멈추는데, 그러면 나머지가 없는 채로
**스스로는 앞뒤가 맞는 파일**이 나오기 때문이다. 건수도 맞고 검증값도 그 상태로
계산된다. 그래서 **파일 바깥에서 온 수**를 따로 적어둬야 한다.

예전 파일에는 `sourceCount`가 없다. 없으면 이 확인을 건너뛴다. 새 검사를 들이면서
예전 파일을 못 열게 만들면 "대화가 앱보다 오래 산다"는 목적과 어긋난다.

메시지가 만 개를 넘어도 되도록 **한 번에 다 읽지 않고 흘려가며** 쓰고 읽는다.

### 6.3 되돌리기

```
파일 고르기
   │
   ▼
형식과 버전 확인 ──── 안 맞으면 ──▶ "이 파일은 이 앱이 만든 게 아니에요"
   │
   ▼
검증값 대조 ──────── 어긋나면 ──▶ "파일이 손상됐어요. 그래도 불러올까요?"
   │                                        │ (사용자가 원하면)
   ▼                                        ▼
한 건씩 넣기 (id가 이미 있으면 건너뛴다)
   │
   ▼
결과 알리기: "1,523건 중 1,200건을 새로 넣었어요. 323건은 이미 있었어요."
```

**겹쳐도 안전하다.** 같은 파일을 두 번 불러도 메시지가 두 배가 되지 않는다. id가 기준이기 때문이다.

**멀쩡한 파일이면 한 건이라도 이상할 때 하나도 넣지 않는다.** 반쯤 넣고 알려주면
이미 늦다. 먼저 전부 확인하고 통과해야 넣는다.

**"그래도 불러올까요?"로 들어온 경우는 다르다.** 이때는 읽을 수 없는 한 건 때문에
나머지를 버리지 않는다. 되살릴 수 있는 것만 넣고 몇 건을 못 읽었는지 알린다.
거절만 하면 그 파일이 하나뿐일 때 통째로 잃기 때문이다.

> 1,523건 중 1,200건을 넣었어요.
> 6건은 읽을 수 없었어요.

다만 **파일을 뜯지도 못하면 이 길도 없다.** 건질 것이 없어서 억지로 넘어가도
할 수 있는 게 없다.

내 프로필까지 덮어쓸지는 물어본다. 상대 기기의 보관 파일을 잘못 불러와 내 캐릭터가 바뀌는 일을 막는다.

### 6.4 자동 보관

사용자가 잊어도 최소한은 남게 한다.

- 앱이 뒤로 갈 때마다 마지막 자동 보관 시각을 확인한다. 24시간이 지났으면 새로 만든다.
- 앱 내부의 **문서 폴더**에 저장한다. 아이폰에서는 파일 앱을 통해 사용자가 직접 꺼낼 수 있는 위치다.
- 최근 3개만 남기고 오래된 것은 지운다.
- 만드는 데 시간이 걸리므로 화면을 막지 않는다.

### 6.5 만료 전 알림

아이폰에서 앱을 설치한 날짜를 기록해둔다. 7일 중 4일이 지나면 앱을 열 때 한 번 알린다.

> **3일 뒤면 이 앱이 열리지 않아요.**
> 대화를 파일로 꺼내두면 다시 설치한 뒤에도 그대로 볼 수 있어요.
> [지금 꺼내기] [나중에]

이 알림에서 바로 내보내기가 실행된다. 설정 화면까지 찾아 들어가게 하지 않는다.

## 7. 입력 중 표시

- 글자를 치기 시작하면 `typing`을 보낸다. 그 뒤 3초에 한 번씩만 다시 보낸다. 글자마다 보내면 낭비다.
- 받은 쪽은 5초 동안 새 신호가 없으면 표시를 지운다.
- 블루투스로 붙어 있을 때는 이 신호를 아예 보내지 않는다. 좁은 길을 실제 대화에 양보한다.

## 8. 읽음 표시

- 화면에 메시지가 실제로 보이고 앱이 앞에 있을 때만 읽음으로 친다.
- 여러 건이 한꺼번에 읽히므로 **묶어서 한 번에** 보낸다.
- 읽음 신호가 못 갔다고 해서 다시 보내지는 않는다. 중요도가 낮고 다음 신호가 덮어쓰기 때문이다.
