# 돌아보기

> 상태: 정리 · 2026-10-12

이 저장소를 닫으며 남겨둔다. 무엇을 하려 했고, 어떻게 만들었고, 실제 비행에서
어떻게 됐고, 그 뒤에 무엇을 했는지. 나중에 비슷한 것을 만들 때 이 문서부터 읽는다.

**한 줄로**: 4일 동안(실제로는 하루 반) 147개 커밋으로 글·사진·음성·이모티콘이
오가는 앱을 두 폰에 올렸지만, **비행기에서는 자리가 멀어 블루투스가 거의 이어지지 않아
대화를 하지 못했다.** 그 비행기에는 기내 Wi-Fi 가 있었는데, 그 길을 처음부터 지워둔
탓에 쓰지 못했다.

---

## 1. 무엇을 하려 했나

비행기에서 **떨어져 앉은 두 사람**이 인터넷 없이 대화한다. 한 사람은 안드로이드,
한 사람은 아이폰이다.

처음부터 걸려 있던 조건

| 조건 | 무엇을 뜻했나 |
|---|---|
| 인터넷이 없다 | 서버·푸시·원격 설정·오류 수집 전부 못 쓴다 |
| 안드로이드 ↔ 아이폰 | Wi-Fi Direct·Multipeer·Nearby·블루투스 클래식이 다 막힌다 |
| 아이폰 앱을 무료 서명으로 깐다 | 7일마다 만료된다. 유료 권한(멀티캐스트, 지정 Wi-Fi 붙이기)을 못 쓴다 |
| 두 사람이 말을 나눌 수 없다 | 화면 글만 보고 각자 연결에 성공해야 한다 |
| 비행기 안에서는 고칠 수 없다 | 버그를 찾으면 그걸로 끝이다 |
| 출발이 코앞이다 | 2026-09-17 밤에 시작해 2026-09-19 새벽에 마지막 빌드를 올렸다 |

## 2. 어떻게 만들었나

### 방식

- **명세 먼저.** 첫 커밋이 명세 9개와 작업 카드 25장이다. 명세에 없는 것은 만들지
  않고, 다르게 만들어야 하면 명세부터 고쳤다(`CLAUDE.md`).
- **작업 카드 한 장 = 커밋 하나 이상.** 카드마다 "끝난 걸 어떻게 아는가" 를 적어두고
  그걸 확인한 뒤 닫았다([tasks/README.md](./tasks/README.md)).
- **층을 나눴다.** `domain` → `application` → `infrastructure`/`presentation`. 통신과
  메시지 규칙이 React Native 없이 돌아서 컴퓨터에서 시험하고, 브라우저 데모에도 그대로
  얹을 수 있었다([03-architecture.md](./03-architecture.md)).
- **규칙을 검사 도구로 묶었다.** 층 의존(`check:deps`), 켜자마자 도는 길의 네이티브
  모듈(`check:native`), 화면 코드의 색(`check:tokens`)을 `pnpm verify` 하나로 돌렸다.
- **AI 와 함께 만들었다.** 실기기에서 잡은 것은 바로 `CLAUDE.md` 의 "실기기에서 잡힌
  것들" 에 적어 다시 밟지 않게 했다.

## 3. 흐름

### 2026-09-17 밤 — 명세와 뼈대

명세와 카드 25장을 쓰고 T01~T06(뼈대, 디자인 토큰, 메시지·연결 도메인, 메시지 절차,

블루투스는 "핫스팟을 못 쓸 때 글만이라도" 가는 보조였다.

T07~T14. 봉투 형식과 바이트 자르기, Wi-Fi 로 상대 찾기, 자동 재연결, 캐릭터,
아이콘, 첫 실행 안내, 대화 화면, 연결 상태. 01:39 에 "글로 대화하는 앱이 섰다".

### 2026-09-18 낮 — 넓혔다

맥을 상대 폰처럼 쓰는 도구, 메시지가 사라지는 경로 막기, 역할을 기기가 정하기,
대화 보관(T19), 통화·영상(T15~T18), 사진(T22), 이모티콘(T23), 낙서·콕 찌르기(T24),
사파리로 대화하는 비상 길(T21), 블루투스 보조(T20), 알림과 배터리, 두 기기를 끝까지
돌리는 시험, 브라우저 데모.

**돌아보면 이때 범위가 가장 넓어졌다.** 통화·영상·낙서·비상 웹 채팅은 결국 비행기에서
못 쓰는 기능이 됐다.

### 2026-09-18 저녁 — 핫스팟이 안 켜진다

실제 갤럭시로 해보니 **비행기 모드에서 핫스팟 메뉴가 잠겼다.** Wi-Fi 를 손으로 켜도,
핫스팟을 먼저 켜고 비행기 모드를 켜도 안 됐다([04-transport-spec.md](./04-transport-spec.md) 1.1).

그래서 블루투스를 **보조에서 본선으로** 올렸다. 같은 밤 남의 블루투스 대화 앱(bitchat)으로
**엘리베이터 시험**을 했다. 집 끝에서 끝(벽 하나)은 이어졌고, 금속 상자 안에서는
끊겼다가 나오자 몇 초 만에 다시 붙었다(04 문서 4.1.1.1).

### 2026-09-18 밤 ~ 09-19 새벽 — 두 폰에 올리고 실기기 버그를 잡았다

아이폰 빌드를 살리느라 Expo SDK 를 56 으로 내리고 Xcode 버전을 고정하고 원격 푸시
권한을 뗐다. 두 폰에 올린 뒤부터는 실기기에서만 보이는 버그가 줄줄이 나왔다.

- 블루투스를 **아예 시도조차 안 했다.** Wi-Fi 가 여는 쪽에서 상대 없이도 "열림" 이라
  거기서 멈췄다
- 이어지지도 않았는데 **이어졌다고** 했다
- 알리기가 실패해도 성공으로 보고했다
- 아이폰이 블루투스가 켜지기 전에 찾기를 시작해 즉시 실패하고 굳었다
- 첫 화면을 못 넘어갔다(식별자를 못 만들고 있었다)
- `Modal` 이 안드로이드에서 그려지는 자리와 눌리는 자리가 어긋났다
- 사진 조각 줄을 두 스레드가 잠금 없이 만져 조각이 사라졌다

이걸 고치면서 블루투스로 **사진·음성까지 작게 줄여** 보내게 됐다. 홈 화면 이름을
SkyTalk 으로 바꿨고, 05:22 에 마지막 빌드를 두 폰에 올렸다. 이때 두 폰은 **집 안 거리에서**
블루투스로 대화가 됐다.

## 4. 실제로 써본 결과 — 비행

2026-09-19 의 마지막 빌드를 두 폰에 올리고 비행기를 탔다.

- **자리가 멀었다.** 블루투스가 거의 이어지지 않았다
- 메시지를 **한 개씩쯤** 주고받았고, 나머지 시간은 앱이 계속 연결만 시도했다
- 결국 이 앱으로는 대화를 하지 못했다

그런데 탑승한 항공기에는 **기내 Wi-Fi 가 있었다.** 인터넷은 안 되지만 영화·음악을 개인
기기로 보는 서비스용이다. 두 폰이 같은 Wi-Fi 에 붙으면 같은 사설망이니, 손님끼리 막아두지만
않았다면 Wi-Fi 로 대화할 수 있었다. **그 생각을 비행기 안에서도 하지 못했다.**

손님끼리 막혀 있었는지는 끝내 모른다. 그날 확인하지 않았다.

## 5. 왜 실패했나

### 5.1 기내 Wi-Fi 를 확인하지 않고 지웠다

[02-tech-decisions.md](./02-tech-decisions.md) D1 의 후보 표에 기내 Wi-Fi 는 첫 줄에
**"대부분 단말끼리 통신 차단 — 기대할 수 없다"** 로 적혀 있다. 근거는 없었다.

같은 D1 바로 아래에는 핫스팟 일을 두고 "문서에서 검증 안 된 추측을 사실처럼 적어둔
탓에 이걸 늦게 알았다. **이후로는 확인하기 전까지 결론을 적지 않는다**" 고 적었다.
그 다짐을 쓴 문서 안에서 같은 실수가 그대로 남아 있었다.

2026-10-12 에 찾아보니 근거는 이랬다.

- 공용·손님용 Wi-Fi 에서 손님끼리 막는 설정(AP isolation)은 흔한 보안 관행이다
- 하지만 **기내 Wi-Fi 에서 얼마나 켜는지 보여주는 자료는 찾지 못했다.** 항공사나 장비
  업체가 공식으로 밝힌 것도 없었다
- 오래된 실제 사례(2015 년 한 항공사의 기내 Wi-Fi)는 오히려 **손님끼리 다 보였다**
- 2026 년 NDSS 논문(AirSnitch)은 이 설정을 우회할 수 있다고 보였다. 막아둔 망이라도 완벽하지는 않다

즉 "기대할 수 없다" 가 아니라 **"타봐야 안다"** 였다. 탔을 때 5분이면 확인할 수 있었다.

### 5.2 하나뿐인 길을 실제 조건에서 재보지 않았다

블루투스가 본선이 된 뒤 잰 거리는 **집 끝에서 끝**뿐이다. 비행기 좌석은 사람 몸과
의자가 전파를 먹는다. 04 문서에도 "비행기는 집보다 나쁘다고 보는 편이 안전하다" 고
적어두기만 하고, 좌석 몇 줄 떨어진 거리를 비슷한 곳(버스, 기차, 강의실)에서 재보지 않았다.

길이 하나뿐이면 그 길이 막히는 순간 앱 전체가 끝난다. **"덤 하나 때문에 대화를 못 하는
것이 가장 나쁜 일"** 이라고 `CLAUDE.md` 에 써두고, 정작 길 자체는 하나만 남겨뒀다.

### 5.3 전제가 늦게 깨졌다

핫스팟이 비행기 모드에서 안 켜진다는 것을 **시작하고 하루가 지나서** 알았다. 첫 명세를
쓰기 전에 폰 하나로 1분이면 확인할 일이었다. 그 하루 동안 핫스팟을 전제로 한 화면 안내,
핫스팟 이름 알려주기, 핫스팟 꺼짐 알아채기가 만들어졌다가 걷혔다.

### 5.4 범위가 넓었다

출발까지 하루 반이었는데 통화·영상·낙서·비상 웹 채팅·음성 메시지까지 만들었다. 대부분
코드로는 완성됐지만 비행기에서 쓸 수 없거나 확인하지 못했다. 그 시간이 연결을 여러 길로
만들고 실제 거리에서 재는 데 갔다면 결과가 달랐을 수 있다.

### 5.5 비행기 안에서 길을 바꿀 수단이 없었다

블루투스가 안 될 때 사람이 할 수 있는 일이 없었다. 화면 도움말은 "블루투스를 켜라,
너무 멀면 안 닿는다" 뿐이었다. 다른 길(기내 Wi-Fi)로 넘어가라는 안내도, 그 길을 쓸
코드도 앱에 없었다. 집에서 쓰던 Wi-Fi 길이 앱에 남아 있었지만 핫스팟 전제로 짜여 있어 기내망에서는
상대를 못 찾았을 수 있다(6장에서 고친 것들).

## 8. 다시 한다면

### 시작하기 전에 재본다

- 쓰려는 길이 **비행기 모드에서 켜지는지** 폰으로 먼저 본다(핫스팟은 1분이면 알았다)
- 비행기 좌석 거리에서 블루투스가 닿는지 **비슷한 곳에서 잰다**
- "기대할 수 없다" 고 적기 전에 근거를 찾는다. 없으면 "타봐야 안다" 로 적고 탔을 때 볼 것을
  점검표에 넣는다

### 길을 여러 개 둔다

- 블루투스와 기내 Wi-Fi 를 처음부터 같이 연다(지금은 그렇게 돼 있다)
- 한 길이 안 될 때 **사람이 할 수 있는 일**을 화면에 적는다(다른 Wi-Fi 에 붙기, 자리 옮기기)

### 비행기에서 볼 것 (다음에 탄다면)

1. 두 폰을 기내 Wi-Fi 에 붙인다. 아이폰은 로그인 창을 닫고 "인터넷 없이 사용"
2. 망 훑어보기 앱(Fing 같은 것)으로 **상대 폰이 보이는지** 본다. 보이면 Wi-Fi 길이 된다
3. 앱을 열어 맨 위 띠가 "Wi-Fi 로 이어져 있어요" 가 되는지 본다
4. 블루투스가 닿는 거리를 좌석 몇 줄 단위로 적어둔다

### 남겨둔 것

- **새 식별자로 처음 빌드할 때** `pnpm expo prebuild --clean` 으로 `ios/`·`android/` 를 새로
  만든다. 폰에는 새 앱으로 깔린다
- 기내 Wi-Fi 길은 실기기 확인 전이다(집 공유기로 먼저 해볼 수 있다)
- 해볼 수 있는 것: 블루투스를 양쪽 다 알리고 찾기(04 문서 4.1.1.2), 주소를 손으로 넣는 마지막
  수단, 두 폰이 다 안드로이드일 때 Wi-Fi Direct(02 문서 D1)
- 통화·영상(T15~T18)은 코드만 있고 여는 단추가 없다
