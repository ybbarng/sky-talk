# 테스트

> 상태: 확정 · 최종 수정 2026-09-19

## 1. 무엇을 지키려는 것인가

이 앱은 **고칠 기회가 한 번뿐이다.** 비행기 안에서 버그를 발견하면 그걸로 끝이다. 앱 스토어 업데이트도, 서버 수정도 없다.

그래서 테스트의 목적은 "커버리지 숫자"가 아니라 **비행기에서 벌어질 일을 땅 위에서 미리 겪어보는 것**이다. 그 기준으로 어디에 힘을 줄지 정한다.

## 2. 어디에 힘을 주는가

```
        적게 ┌──────────────┐
             │  손으로 확인  │  실제 두 폰으로. 자동화 못 하는 것 ★ 여기서만 잡히는 것이 많았다
             ├──────────────┤
             │  화면 테스트  │  주요 흐름만
             ├──────────────┤
             │  이어붙임     │  ★ 두 기기가 대화하는 전 과정
             ├──────────────┤
        많이 │  단위 테스트  │  ★ 도메인과 응용 계층 전부
             └──────────────┘
```

- **도메인·응용 계층**은 진짜 블루투스 없이 전부 시험할 수 있다. 앱의 규칙이 여기 모여 있다.
- **이어붙임 테스트**는 두 기기를 흉내내어 주고받는 전 과정을 컴퓨터에서 돌린다. 이 앱의 가장 큰 위험이 "두 기기 사이"에 있으므로 여기가 가장 값지다.
- **손으로 확인**은 적지만 빼놓을 수 없다. 2026-09-19 에 잡은 굵직한 버그(찾기 시작 시점, 조각 유실, 녹음기 생성자, 재생 확장자, 화면 자리 어긋남)는 전부 실기기에서만 드러났다. 6장의 점검표가 그 목록이다.

화면 테스트는 주요 흐름만 본다. 버튼 색 같은 것까지 시험하면 화면을 고칠 때마다 테스트가 깨져서 오히려 손해다.

## 3. 반드시 시험하는 것

### 도메인

| 대상 | 무엇을 확인하나 |
|---|---|
| `Message` | 잘못된 내용으로는 만들어지지 않는다 |
| `DeliveryState` | 읽음에서 전달됨으로 되돌아가지 않는다. 모든 전이 조합을 확인 |
| `Conversation` | 같은 id를 두 번 받지 않는다. 순번의 빈틈을 정확히 찾아낸다 |
| `ConnectionState` | 상태 전이가 규칙을 따른다. 다시 붙는 간격이 1, 2, 4 … 30초로 는다 |
| `FlightTimer` | 출발·도착 시각에서 남은 길이와 전체 길이를 센다. 자정을 넘는 비행, 이미 출발한 뒤, 도착 뒤를 다룬다. "출발한 지" 글 |
| `Character` | 고른 값이 유효하다 |

### 응용

| 대상 | 무엇을 확인하나 |
|---|---|
| `SendMessage` | **보내기 전에 저장한다.** 전송이 실패해도 메시지가 남는다 |
| `ReceiveMessage` | 같은 메시지가 두 번 와도 하나만 남는다 |
| `ConversationSync` | 인사에 이름·캐릭터·상태 메시지가 실려 간다. 상대가 "몇 번까지 받았다" 고 하면 그 뒤를 다시 보낸다 |
| `FlushPendingMessages` | 쌓인 순서대로 나간다 |
| `SendPhoto` | 메시지를 먼저 보내고 조각을 나중에 보낸다. 작게 고르면 훨씬 작게 줄인다. 안 고르면 중간이다 |
| `ReceiveAsset` | 순서가 뒤바뀌어 와도 제자리에 담는다. 같은 조각이 두 번 와도 된다. 다시 붙으면 못 받은 것만 달라고 한다 |
| `ExportConversation` | 만 건을 내보내도 메모리가 터지지 않는다 |
| `ImportConversation` | 같은 파일을 두 번 불러도 두 배가 되지 않는다. 검증값이 어긋나면 멈춘다 |

### 통신 규약

**이게 가장 중요한 묶음이다.**

| 무엇 | 어떻게 |
|---|---|
| 바이트 자르기 | 한 번에 온 것, 잘려서 온 것, 붙어서 온 것을 전부 올바로 나눈다 |
| 모르는 봉투·모르는 항목 | 새 종류가 와도, 예전 앱이 코드를 실어 보내도 연결이 유지된다 |
| 망가진 내용 | 형식 검사에서 걸러지고 앱이 죽지 않는다 |
| 순번 | 빠짐·겹침·뒤바뀜을 각각 올바로 다룬다 |
| 블루투스 조각내기 | 조각내고 다시 붙이면 원래 값과 같다. 조각 번호가 두 바이트라 65,535조각까지 |
| 조각 유실 | 하나가 안 오면 그 묶음을 버린다 |
| 찾기 차례 | 여는 쪽은 알리기부터, 붙는 쪽은 찾기부터. 안 되면 반대로 |
| 켜질 때까지 기다림 | "모름" 상태에서는 찾기를 시작하지 않는다. 꺼져 있으면 돌아서지 않고 무엇을 누르면 되는지 알린다 |
| 접지 않기 | 한 바퀴 못 찾으면 쉬고 다시 찾는다. 오류가 나면 점점 길게 쉰다. 끊기면 다시 찾는다. 끈 뒤에는 더 안 찾는다 |
| 심장박동 | 한참 조용하면 끊긴 것으로 보고 다시 찾는다. 무엇이든 받고 있으면 끊긴 것으로 보지 않는다 |
| 양보 | 알리는 쪽은 줄이 짧아질 때까지 다음 사진 조각을 안 넣는다. 글은 줄을 안 본다 |
| 여러 길 | 못 연 길이 스스로 이어지면 옮긴다. 블루투스로 이어진 뒤 Wi-Fi 가 되뇌는 "찾는 중" 에 흔들리지 않는다. 이미 이어져 있으면 다시 열어도 그대로다 |

**아무 바이트나 던져도 앱이 죽지 않는지**를 별도로 확인한다. 무작위 값을 수천 번 넣어보는 방식(퍼즈)을 쓴다.

### 두 기기가 대화하는 전 과정

가짜 연결 두 개를 이어 붙여 한쪽에서 보낸 것이 다른 쪽에 도착하는지 확인한다. 진짜 블루투스가 필요 없다.

```
시험하는 장면:
  · 인사부터 메시지 한 통이 도착하기까지
  · 도중에 끊겼다 붙었을 때 놓친 것이 채워지는가
  · 양쪽이 동시에 보낼 때 순서가 유지되는가
  · 한쪽만 재시작했을 때 다시 붙는가
  · 100통을 연달아 보낼 때 순서가 유지되는가
  · 사진 조각이 뒤바뀌어 와도 다 모이는가
```

### 화면

| 무엇 | 어떻게 |
|---|---|
| 설명 창 | 열고 닫힌다. 단추가 눌린다 |
| 입력칸 | 도구 줄이 펼쳐지고 접힌다. 고르거나 글을 쓰면 접힌다 |
| 연결 단계 | 블루투스가 꺼져 있으면 켜라고 하고, 모르면 기다리는 쪽으로 말한다 |
| 끊김 알림 | 잠깐 끊긴 것은 넘어간다. 블루투스가 꺼진 것은 더 빨리 알린다 |
| 콕 찌르기 | 받으면 떤다. 설정에서 끄면 안 떤다. 앱을 안 보고 있으면 잠금 화면에도 뜬다 |
| 시각 표시 | 같은 분 묶음의 마지막에만, 분이 바뀌면 앞 말에도 |

## 4. 시간과 무작위를 다루기

테스트가 어떤 날 갑자기 실패하는 일을 막는다.

- **시간**: `Date.now()`를 직접 부르지 않는다. `Clock`을 주입받아 쓴다. 테스트에서는 가짜 시계로 돌린다. 다시 붙는 간격이나 심장박동을 시험할 때 진짜로 기다리지 않는다.
- **식별자**: ULID를 만드는 것도 주입받는다.
- **무작위**: 씨앗을 고정한다. 실패하면 같은 순서로 다시 재현할 수 있다.

응용 계층이 요구하는 약속마다 가짜 구현을 하나씩 둔다. `test/fakes/` 에 있다.

블루투스 무전기 자체는 `BleMessageTransport.test.ts` 안에서 관리자·기기·알리기 모듈을 흉내 내어 시험한다. 상태가 "모름" 이었다가 켜지는 것, 상대가 나타나는 것, 끊기는 것, 오류가 나는 것을 시험이 일으킬 수 있다.

## 5-1. 맥을 상대 폰으로 쓰기

`scripts/peer-simulator.ts` 가 **앱과 똑같은 코드로 말한다.** Wi-Fi(TCP) 길만 흉내 내므로 집에서 규약을 확인할 때 쓴다.

```bash
pnpm peer --host              맥이 받는 쪽
pnpm peer --guest --to <주소>  맥이 거는 쪽
```

블루투스 길은 이걸로 확인할 수 없다. 두 폰이 있어야 한다.

## 5-2. 남의 앱으로 먼저 재보기

**"비행기 모드에서 BLE 가 되긴 하는가"** 는 우리 코드보다 먼저 확인할 일이었다. bitchat 을 두 폰에 깔고 비행기 모드 + 블루투스만으로 재봤다(2026-09-18). 20평 집 끝에서 끝, 엘리베이터 왕복 재연결까지 됐다. 그래서 방향을 접지 않았다.

**다만 bitchat 을 우리 앱과 같이 켜두면 안 된다.** 같은 블루투스 링크를 써서 우리 연결이 끊긴다(2026-09-19 확인). 재본 뒤에는 두 폰 모두 완전히 종료한다. 삭제는 하지 않는다. 우리 앱이 안 될 때의 대비책이다(끊긴 동안 보낸 메시지를 버린다는 차이가 있다).

## 6. 자동으로 못 하는 것 — 실기기 점검표

실제 기기가 있어야만 확인되는 것들이다. 2026-09-19 에 이 순서로 확인했다.

```
연결
  □ 두 폰 다 비행기 모드 + 블루투스만 켜고 이어진다   ← 가장 중요
  □ bitchat 을 두 폰 모두 완전히 껐다
  □ 이름 옆 점이 초록이고, 상대 이름·캐릭터·상태 메시지가 보인다
  □ 한쪽 블루투스를 껐다 켜면 40초 안에 끊김이 뜨고 저절로 다시 붙는다
  □ 앱을 껐다 켜도 다시 붙는다 (아이폰은 이어져 있다고 믿는 채 남을 수 있어
     안드로이드가 켜질 때 옛 연결을 떼어낸다)
  □ 설정에서 이름·상태 메시지를 바꾸면 상대 화면에 바로 반영되고 연결이 흔들리지 않는다

메시지
  □ 글이 오간다 (양쪽 다). 끊긴 동안 보낸 말이 다시 붙을 때 도착한다
  □ 콕 찌르면 상대 폰이 떨린다 (아이폰은 시스템 햅틱이 꺼져 있어도)
  □ 이모티콘을 길게 누르면 옆에 뜻이 뜬다
  □ 키보드가 뜨면 입력칸과 대화가 같이 올라간다 (안드로이드 포함)
  □ 도구 줄을 여닫거나 내가 말을 보내도 마지막 말이 잘리지 않는다

사진·음성
  □ 사진을 "작게" 로 보내면 30초 안팎에 도착하고 양쪽 퍼센트가 움직인다
  □ 사진이 가는 동안 보낸 글이 몇 초 안에 도착한다
  □ 다 받은 사진을 눌러 크게 보고 두 손가락으로 벌린다
  □ 음성 메시지를 녹음 창에서 녹음해 보내고, 받은 쪽에서 들린다
  □ 20초가 되면 녹음이 저절로 끝난다

비행·설정
  □ 출발·도착 시각을 넣으면 두 화면에 같은 비행기가 뜬다
  □ 남은 시간 글을 누르면 출발한 지 얼마나 됐는지로 바뀐다
  □ 대화 비우기 뒤에도 상대 화면과 꺼낸 파일에는 남아 있다

보관
  □ 내보낸 파일을 공유 창으로 Google Drive 에 올릴 수 있다
  □ 내보낸 파일을 다시 불러오면 대화가 그대로다
  □ 아이폰 앱을 덮어쓰기로 다시 깔아도 대화가 남는다

버티기
  □ 한 시간 동안 연결을 유지한다
  □ 대기 상태에서 배터리가 시간당 5% 이내로 준다
```

### 손으로 확인할 때 알아둘 것

- 안드로이드 단추는 `adb shell input tap` 이 안 먹는 경우가 있다. `input swipe X Y X+2 Y+2 150` 으로 2픽셀 움직여 누른다. 화면 글은 `uiautomator dump` 로 읽는다.
- 안드로이드가 알리는지는 `adb logcat` 에서 `BLE_GAP ... ADV_SET_START :: appName: com.ybbarng.skytalk` 로 본다. 우리 앱 프로세스의 `BluetoothGattServer` 줄에서 상대가 붙었는지도 보인다.
- 아이폰 로그는 도구가 없어 못 본다. 아이폰 쪽 버그는 코드를 읽어 잡았다.
- 아이폰이 잠겨 있으면 앱을 못 켠다(`BSErrorCodeDescription = Locked`). 잠금을 풀고 한다.
- 아이폰은 시작 화면을 캐시해서 덮어 설치한 뒤에도 옛 그림이 뜰 수 있다. 재부팅하면 사라진다.

## 7. 어느 정도까지 시험하나

숫자를 목표로 삼지 않되, 층별로 기대치를 둔다.

| 층 | 기대 | 왜 |
|---|---|---|
| domain | 95% 이상 | 순수한 코드라 안 할 이유가 없다 |
| application | 90% 이상 | 앱의 절차가 여기 있다 |
| (분기만) | 75~90% | 아래 설명 참고 |
| infrastructure — 규약·무전기 판단 부분 | 90% 이상 | 바이트를 다루고 차례를 정하는 곳이라 실수가 잦다 |
| infrastructure — 기기에 닿는 부분 | 시험하지 않음 | 진짜 기기가 필요하다. 6장으로 확인 |
| presentation | 주요 흐름만 | 화면은 자주 바뀐다 |

**분기(branch) 기준만 낮게 잡은 이유**: 측정 도구(v8)가 기본값과 옵셔널 파라미터까지 분기로 센다. 숫자를 채우는 대신 "무엇이 잘못될 수 있는가"를 보고 테스트를 고른다.

## 8. 돌리는 법

```bash
pnpm test              # 한 번 돌린다
pnpm test:watch        # 고칠 때마다 다시 돌린다
pnpm test:coverage     # 어디가 안 시험됐는지 본다
pnpm typecheck         # 타입
pnpm lint              # 형식과 흔한 실수
pnpm check:deps        # 층이 규칙을 어기지 않는지
pnpm check:native      # 켜자마자 도는 길에 네이티브 모듈이 없는지
pnpm check:tokens      # 화면 코드에 색을 직접 적지 않았는지
pnpm verify            # 위를 전부
```

커밋할 때 `lint`와 `typecheck`가 자동으로 돈다. lefthook이 한다.

## 9. 테스트를 쓰는 규칙

- 이름은 **무엇을 보장하는지** 한국어로 적는다. `"켜질 때까지 기다렸다가 찾는다"`처럼.
- 한 테스트는 하나만 확인한다.
- 준비·실행·확인 세 덩어리로 나누고 빈 줄로 구분한다.
- 가짜 부품을 만들 때 실제 구현과 같은 인터페이스를 쓴다. 그래야 실제가 바뀌면 가짜도 같이 깨진다.
- 내부 구현을 시험하지 않는다. 밖에서 보이는 행동만 시험한다.
- 실기기에서 잡은 버그는 **고치기 전에 그 상황을 테스트로 먼저 적는다.** 오늘 잡은 것들이 이 문서 3장에 그렇게 들어갔다.
