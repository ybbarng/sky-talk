# 기술 선택과 근거

> 상태: 확정 · 최종 수정 2026-09-19

왜 이렇게 골랐는지를 남겨둔다. 나중에 "이거 왜 이렇게 했지?" 싶을 때 여기를 본다.
각 항목은 **무엇을 정했나 / 왜 / 대신 무엇을 포기했나** 순서로 적는다.

## D1. 두 기기를 잇는 방법 — BLE 가 유일한 길

### 정한 것 (2026-09-18 에 바꿨다)

비행 중에는 **블루투스 저전력(BLE)** 이 유일한 길이다. 안드로이드가 알리고
아이폰이 찾는다. 글·이모티콘·콕 찌르기는 바로 가고, 사진과 음성 메시지는
작게 줄여 천천히 간다. Wi-Fi(핫스팟 + TCP)는 **집에서 준비할 때만** 쓴다.

### 왜

후보를 전부 따져봤다.

| 후보 | 안드로이드↔아이폰 | 속도 | 판정 |
|---|---|---|---|
| 기내 Wi-Fi | 대부분 단말끼리 통신 차단 | — | 기대할 수 없다 |
| Wi-Fi Direct | 아이폰이 지원 안 함 | — | 불가 |
| Apple Multipeer | 아이폰끼리만 | — | 불가 |
| Google Nearby | 안드로이드 위주 | — | 불가 |
| 블루투스 클래식(SPP) | 아이폰은 애플 인증 부품에만 허용 | — | 불가 |
| **BLE (GATT)** | **양쪽 다 가능** | 초당 수 KB | **채택. 이것뿐이다** |
| ~~핫스팟 + IP 통신~~ | 양쪽 다 가능 | 수십 Mbps | **비행기 모드에서 안 켜진다** |

처음에는 핫스팟을 주 경로로 잡았다. 실제 기기(갤럭시)에서 해보니 **비행기 모드에서는
핫스팟 메뉴 자체가 잠긴다.**

| 해본 것 | 결과 |
|---|---|
| 비행기 모드 → 핫스팟 | 잠김 |
| 비행기 모드 → Wi-Fi 를 손으로 켜기 → 핫스팟 | **잠김** |
| 핫스팟을 먼저 켜기 → 비행기 모드 | **핫스팟이 꺼진다** |
| 비행기 모드에서 열리는 것 | **블루투스 테더링만** |

블루투스 테더링은 쓸모가 없다. 아이폰은 거기 들어가는 화면이 없다. 문서에서 검증 안 된
추측을 사실처럼 적어둔 탓에 이걸 늦게 알았다. 이후로는 확인하기 전까지 결론을 적지 않는다.

### 2026-10-12 에 덧붙인다 — 기내 Wi-Fi 도 길이다

위 표의 "기내 Wi-Fi — 대부분 단말끼리 통신 차단" 은 **확인하지 않은 일반론이었다.** 실제 비행에서
자리가 멀어 블루투스가 거의 안 이어졌는데, 그 비행기에는 인터넷 없는 기내 Wi-Fi 가 있었다.
찾아보니 기내 Wi-Fi 가 손님끼리 막는다는 근거는 없었고, 막지 않은 실제 사례가 있었다.
지금은 블루투스와 기내 Wi-Fi 를 같이 열고 먼저 이어지는 쪽을 쓴다
([04-transport-spec.md](./04-transport-spec.md) 1.2). 무엇이 어떻게 됐는지는
[10-retrospective.md](./10-retrospective.md) 에 있다.

### 2026-09-19 에 실제로 이어졌다

두 폰이 BLE 로 안 이어지던 원인은 아이폰 쪽 라이브러리가 켜지기 전에 찾기를 시작하면
즉시 실패한다는 것이었다. 켜질 때까지 기다리고, 못 찾아도 접지 않고, 끊기면 다시 찾게
고쳤다. 이어진 뒤에는 10초마다 눈에 안 보이는 심장박동을 주고받아 진짜 연결 상태를 본다.
자세한 것은 [04-transport-spec.md](./04-transport-spec.md) 4장에 있다.

### 두 폰이 다 안드로이드라면 달라진다

Wi-Fi Direct 는 테더링이 아니라 Wi-Fi 기능이라 비행기 모드에서도 될 가능성이 높다.
확인하지 않았으므로 여기에 결론을 적지 않는다. 확인법은 두 폰 다 비행기 모드 + Wi-Fi 켠
채로 설정 → Wi-Fi Direct 에서 서로 보이는지 보는 것이다.

### 포기한 것

- 비행 중 통화(음성·영상). BLE 로는 못 나른다
- 원본 사진을 빨리 보내는 것. 원본은 몇 분이 걸린다고 알리고 사용자가 고른다
- 두 아이폰끼리는 연결할 수 없다. 우리 둘에겐 문제가 아니다

## D2. 통화 — WebRTC 코드는 남기되 준비 중으로 둔다

### 정한 것

`react-native-webrtc` 로 만든 통화 코드는 남아 있다. STUN·TURN 서버는 쓰지 않고
협상 정보는 우리 TCP 소켓으로 주고받는다. **다만 비행기에서는 쓸 수 없으므로**
통화 단추를 누르면 "준비 중" 이라고 알린다. 통화 탭과 영상 통화 단추는 뺐다(2026-09-19).

### 왜

같은 Wi-Fi 안이면 서로의 사설 주소로 바로 닿아 인터넷이 필요한 부분을 전부 도려낼 수
있다. 그런데 비행기에서는 Wi-Fi 가 없고, BLE 는 초당 몇 KB 라 목소리를 나를 수 없다.
준비가 덜 된 기능을 탭으로 내세우면 헷갈리기만 한다.

### 포기한 것

- 비행 중 목소리로 이야기하기. 대신 음성 메시지(20초)가 있다.

## D3. 앱을 만드는 도구 — React Native + Expo (직접 빌드 방식)

### 정한 것

Expo SDK 56 / React Native 0.85 위에 TypeScript로 만든다.

**57 이 아니라 56 인 이유가 있다.** 57 은 아이폰 빌드에 Xcode 26.4 이상을
요구하고, 그건 macOS Tahoe 26.2 이상을 요구한다. 자세한 사정은
[08-build-release.md](./08-build-release.md) 1.1 에 있다.

`expo prebuild`로 네이티브 프로젝트를 만들어 쓴다. **Expo Go 앱으로는 못 돌린다.**
아이콘이나 홈 화면 이름을 바꿨을 때도 `prebuild` 를 다시 돌려야 네이티브에 들어간다.

### 왜

- 한 벌만 짜서 두 기기에 올린다.
- 필요한 네이티브 기능이 전부 라이브러리로 있다: BLE, TCP 소켓, 녹음, WebRTC.
- 알리는 쪽 BLE 모듈(`modules/ble-peripheral`)만 Kotlin·Swift 로 직접 만들었다.

### 포기한 것

- 첫 빌드 설정에 시간이 든다. 네이티브를 건드릴 때마다 다시 빌드해야 한다.

## D4. 메시지 저장 — SQLite

### 정한 것

`expo-sqlite`에 메시지를 저장한다. 설정 같은 작은 값은 파일에 담는다.

### 왜

- 메시지는 시간순으로 쌓이고 계속 늘어난다. 조각조각 읽어오는 일(스크롤)을 잘 하는 건 관계형 저장소다.
- 순서 보장과 중복 방지를 데이터베이스 제약으로 강제할 수 있다.
- 내보내기·되돌리기를 만들 때 질의 한 번으로 전체를 꺼낼 수 있다.

### 알아둘 것

- 동기화에 쓰는 순번(내가 몇 번까지 보냈나, 몇 번까지 받았나)은 메시지 행에서 센다. 그래서 **메시지를 지우면 순번이 0으로 돌아가** 다음 인사 때 상대가 전부 다시 보낸다. "대화 비우기" 가 지우지 않고 감추는 이유다(D12).
- 릴리즈 빌드의 DB 는 `adb` 로 못 꺼낸다. 내보내기가 유일한 길이다.

## D5. 코드 구조 — 클린 아키텍처 + 도메인 주도 설계

### 정한 것

네 겹으로 나눈다: **도메인 → 응용 → 기반 → 화면**. 바깥 겹은 안쪽을 알지만, 안쪽은 바깥을 모른다.

### 왜

이 앱의 핵심 난제는 "연결 방식이 여러 개인데 언제든 바뀐다"는 점이다. 집에서는 Wi-Fi, 비행기에서는 BLE, 아이폰이 만료되면 웹이다. 이걸 화면 코드에 섞어 넣으면 손을 못 대는 상태가 된다.

그래서 **"메시지를 보낸다"는 뜻은 도메인에 두고, "어떤 길로 보내는가"는 갈아 끼울 수 있는 부품으로 분리**한다. 실제로 사진·음성을 BLE 로 나르기로 바꿀 때(D11) 도메인과 화면은 거의 안 건드렸다.

자세한 구조는 [03-architecture.md](./03-architecture.md)에 있다.

### 포기한 것

- 파일과 인터페이스가 늘어난다. 연결 방식이 세 갈래라 이 격식이 실제로 값을 한다.

## D6. 화면 상태 관리 — Zustand

### 정한 것

화면이 보는 상태는 Zustand에 담는다. 서버가 없으니 데이터 패칭 라이브러리는 쓰지 않는다.

### 왜

- 가볍고, 연결 상태처럼 여러 화면이 동시에 보는 값을 다루기 좋다.
- React 바깥(소켓 수신 콜백 등)에서 상태를 바꾸기 편하다. 이 앱은 그런 경우가 많다.

## D7. 화면 꾸미기 — 직접 만든 디자인 토큰 + SVG

### 정한 것

Tailwind 대신 **직접 정의한 토큰과 스타일 함수**를 쓴다. 그림은 `react-native-svg`로 그린다.
`react-native-reanimated` 는 손짓이 직접 끄는 값(사진 확대)에만 쓴다.

### 왜

- 밝은/어두운 화면 전환을 토큰 한 곳에서 다루면 어긋남이 생기지 않는다.
- 캐릭터가 말할 때 입이 움직여야 한다. SVG를 코드로 그려야 가능하다.
- **레이아웃 움직임(들고 나는 효과)은 쓰지 않는다.** 그려지는 자리와 눌리는 자리가 어긋나 단추가 안 눌렸다. 자세한 것은 `Sheet.tsx` 주석과 [03-architecture.md](./03-architecture.md) "화면에서 지키는 것" 에 있다.

## D10. 앱이 핫스팟도 블루투스도 대신 켜주지 못한다

안드로이드 10부터 앱이 핫스팟을 켤 수 없고, 블루투스도 두 운영체제 모두 앱이 대신
못 켠다. 앱은 켜졌는지 **감지**만 하고, 꺼져 있으면 설정 화면으로 데려다준다.
지금은 블루투스가 켜져 있는지를 보고 "블루투스 켜러 가기" 단추를 띄운다.
예전에는 Wi-Fi 사설망에 있는지로 판단했는데, 비행기에서는 Wi-Fi 가 없는 것이 정상이라
멀쩡한 사람에게 켜라고 하게 되어 바꿨다(2026-09-19).

## D11. 사진과 음성 메시지를 BLE 로 나른다

### 정한 것 (2026-09-19)

블루투스로도 사진·음성 조각을 보낸다. 사진은 작게(800px·화질 0.5)·중간·원본 중에
고르고, 음성은 20초까지 녹음한 대로 보낸다. 보내기 전에 얼마나 걸릴지 알리고
사용자가 고른다. 양쪽 말풍선에 퍼센트가 실시간으로 움직인다.

### 왜

그전에는 BLE 에서 막고 Wi-Fi 를 기다렸다. 비행기에서는 Wi-Fi 가 영영 안 열리므로
영영 못 보내는 것이었다. 초당 3KB 남짓이면 작게 줄인 사진 한 장에 30초, 10초 음성에
15초다. 오래 걸려도 가는 편이 낫고, 그 대신 **설명하고 고르게** 한다.

### 그래서 바꾼 것

- BLE 조각 번호를 한 바이트(255조각, 46KB)에서 두 바이트로 넓혔다. 48KB 사진 조각이 통째로 안 들어갔다.
- 쓰기는 응답을 받는다. 응답 없는 쓰기는 버퍼가 차면 조용히 버려져 봉투가 안 모인다.
- 알리는 쪽은 조각을 줄에 세우기만 하면 되므로 한꺼번에 밀어 넣을 수 있는데, 그러면 글이 몇십 초 기다린다. 줄이 짧을 때만 다음 조각을 넣어 글이 끼어들게 했다.

### 포기한 것

- 낙서는 여전히 BLE 로 안 보낸다. 크기에 비해 쓰임이 적다.

## D12. 대화 비우기는 지우지 않고 감춘다

### 정한 것 (2026-09-19)

설정의 "대화 비우기" 는 비운 시각 전의 말을 **화면에서만** 안 보이게 한다. 행은 남는다.

### 왜

동기화 순번을 메시지 행에서 세기 때문에(D4) 지우면 다음 인사 때 상대가 전부 다시 보내
화면이 도로 채워진다. 순번을 따로 저장하는 표를 두면 되지만 비행 전날 표를 바꿀 일은 아니다.

### 포기한 것

- 기기에서 진짜로 지우는 것. 꺼내둔 파일에도 그대로 남는다. 도움말과 확인 창에 적어뒀다.

## D13. 이름은 겉만 SkyTalk 으로 바꾼다

### 정한 것 (2026-09-19)

홈 화면 이름과 블루투스 알림 이름, 권한 안내 문구만 SkyTalk 이다. `app.config.ts` 의
`name`·`slug`·번들·패키지는 `skywalkie` 그대로고, 설정 플러그인
`plugins/withDisplayName.js` 가 표시 이름만 바꾼다.

> 2026-10-12 에 바꿨다. `name`·`slug`·번들·패키지도 SkyTalk(`sky-talk`,
> `com.ybbarng.skytalk`)에 맞췄다. 그때까지 쌓인 대화가 사실상 없어서 새 앱이 되어도
