# T08 — Wi-Fi 연결: 상대 찾기와 TCP

**단계** 연결 · **상태** 코드 완료 · 집에서만 쓰는 길 · **먼저** T07

## 목표

두 폰이 같은 핫스팟에 붙으면 **손으로 아무것도 입력하지 않고** 서로를 찾아 연결된다.

## 근거

[04-transport-spec.md](../04-transport-spec.md) 2장

## 할 일

```
src/infrastructure/transport/wifi/
  TcpMessageTransport.ts     서버 쪽 + 클라이언트 쪽
  TcpServer.ts               안드로이드(호스트)가 받는 쪽
  TcpClient.ts               아이폰(게스트)이 거는 쪽
  UdpPeerDiscovery.ts        소리쳐 부르기
  GatewayProbe.ts            게이트웨이에 바로 걸기
  SubnetScanner.ts           훑어보기
  NetworkInfo.ts             내 IP와 게이트웨이 주소 알아내기
```

### 역할 고정

핫스팟을 연 안드로이드가 **항상 게이트웨이**다. 그래서 안드로이드가 받는 쪽, 아이폰이 거는 쪽으로 고정한다. 누가 먼저 말을 걸지 헷갈릴 일이 없어진다.

### 상대 찾기 — 순서대로

[04-transport-spec.md](../04-transport-spec.md) 2.3의 네 방법을 순서대로 시도한다.

```
1. 게이트웨이에 바로 걸기      대개 1초 안에 끝난다
2. UDP로 소리쳐 부르기         1초 간격으로 최대 10번
3. 사설망 훑어보기             32개씩 동시에, 각 300밀리초
4. 사람이 코드를 읽어주기       위가 전부 실패했을 때
```

하나라도 성공하면 나머지를 멈춘다.

**3번이 오래 걸리므로 진행 상황을 화면에 보낸다.** 사용자가 앱이 멈춘 줄 알면 안 된다. [07-design-system.md](../07-design-system.md) 8장에 그 화면이 그려져 있다.

### 살아있는지 확인

- 5초 동안 말이 없으면 길이 0인 신호를 보낸다
- 15초 동안 아무것도 안 오면 끊긴 것으로 본다
- 끊기면 1, 2, 4, 8, 16, 30초 간격으로 다시 붙는다

### 앱이 뒤로 갔을 때

- 안드로이드: 연결을 유지한다. 통화 중이 아니면 앞에서 도는 서비스 없이도 잠시는 버틴다
- 아이폰: 몇 초 뒤 연결이 끊긴다. 막을 수 없다. **앞으로 돌아오면 빠르게 다시 붙는 것**으로 대응한다

이 차이를 사용자에게 알린다. "아이폰은 앱을 닫으면 메시지를 못 받아요. 받은 메시지는 앱을 열면 도착합니다."

## 테스트

기기가 필요한 부분과 아닌 부분을 나눈다.

**컴퓨터에서 시험하는 것**
- 찾기 순서: 1번이 성공하면 2, 3번을 시도하지 않는다
- 1번이 실패하면 2번으로 넘어간다
- 훑어보기가 32개씩 나눠서 도는지
- 다시 붙는 간격이 정확히 1, 2, 4, 8, 16, 30초인지 (`FakeClock`으로)
- 15초 침묵이면 끊긴 것으로 판단하는지

**실제 기기로 확인하는 것** ([09-testing.md](../09-testing.md) 6장 점검표)
- 핫스팟을 켜고 붙는다
- **비행기 모드에서도 된다** ← 가장 중요
- 핫스팟을 껐다 켜면 자동으로 다시 붙는다

## 하면서 알게 된 것

### 판단을 전부 소켓 바깥으로 뺐다

소켓을 다루는 코드는 컴퓨터에서 시험할 수 없다. 그래서 **시험할 수 있는 것과
없는 것을 갈랐다.**

| 무엇 | 어디 | 시험 |
|---|---|---|
| 주소 계산, 게이트웨이 짐작 | `NetworkAddress.ts` | 가능 |
| 찾는 순서, 묶음 나누기, 역할 정하기 | `DiscoveryPlan.ts` | 가능 |
| 실제로 걸어보기 | `WifiPeerDiscovery.ts` | 기기 필요 |
| 소켓 배선 | `TcpMessageTransport.ts` | 기기 필요 |

기기가 필요한 두 파일에는 **판단이 거의 없다.** 바이트 자르기는 `FrameDecoder`,
형식 검사는 `EnvelopeSchema` 가 하고 여기 남은 건 배선뿐이다.

### 아이폰은 게이트웨이를 알려주지 않는다

`expo-network` 는 내 IP 만 준다. 게이트웨이는 못 얻는다. 그래서 **같은 대역의
`.1` 로 짐작한다.** 안드로이드 핫스팟은 거의 예외 없이 이 모양이고, 짐작이
틀려도 손해가 없다 — 실패하면 다음 방법으로 넘어간다.

덤으로 이 규칙이 **역할까지 정해준다.** 내 주소가 `.1` 이면 내가 핫스팟을 연
쪽이니 받는 역할, 아니면 거는 역할이다. 둘 다 걸거나 둘 다 기다리는 일이 없다.

### 셀룰러로 새는 걸 막았다

`react-native-tcp-socket` 에 `interface: 'wifi'` 옵션이 있다. 아이폰에서
셀룰러가 켜져 있으면 그쪽으로 나가서 사설망 주소에 닿지 못한다. 비행기 모드면
상관없지만 집에서 시험할 때 반드시 걸린다.

### 남은 위험

- **UDP 브로드캐스트가 막힌 기기가 있다.** 그래서 훑어보기를 마지막 수단으로
  둔다. 253개를 32개씩 동시에 걸어 3초쯤 걸린다
- 안드로이드가 백그라운드에서 소켓을 얼마나 오래 살려두는지는 기기마다 다르다.
  [T16](./T16-audio-session.md) 의 앞에서 도는 서비스가 이것도 함께 해결한다
