### 연결 상태 전이

[04-transport-spec.md](../04-transport-spec.md)의 그림 그대로다.

```
idle → searching → handshaking → connected
                        ↑             │
                        └── 실패 ─────┤
                                      │
                   switching ◀────────┤ (더 좋은 길 발견)
                                      │
                    idle   ◀──────────┘ (사용자가 끔)
```

갈아탈 때 지켜야 할 것: **`switching`은 새 길이 열린 뒤에만 `connected`로 간다.** 중간에 메시지를 흘리지 않기 위해서다. 이 규칙을 상태 전이가 직접 강제한다.

### 길 고르기 점수

```ts
score = 기본점수 × 품질계수

기본점수:  wifi 100, ble 40, web 30
품질계수:  신호 세기와 응답 시간으로 0.3 ~ 1.0
```

점수 차이가 **20점 이상 날 때만** 갈아탄다. 안 그러면 두 길 사이를 계속 오간다.

## 하면서 알게 된 것

### "같은 상태로 가면 그대로 둔다"가 한 군데서 틀렸다

상태 전이에 "같은 상태를 다시 요청하면 아무 일도 없다"는 규칙을 두었다.
같은 신호가 두 번 오는 게 흔하기 때문이다.

그런데 `searching → searching` 만은 다르다. **찾는 중에 또 찾기를 부르는 건
"다시 시도"라는 뜻**이라 횟수가 올라야 한다. 안 그러면 기다리는 간격이
1초에서 멈춰서 계속 시도하고 배터리가 준다.

테스트가 이걸 잡았다. `startSearching` 만 공통 규칙을 따르지 않게 했다.

### 길을 고르는 기준이 단순한 순위가 아니다

Wi-Fi 가 무조건 블루투스보다 낫지는 않다. 신호가 없다시피 한 Wi-Fi 보다
멀쩡한 블루투스가 낫다. 그래서 기본 점수에 품질 계수를 곱하고,
아주 나쁜 Wi-Fi 가 멀쩡한 블루투스보다 낮아질 수 있게 했다.

다만 점수가 0까지 떨어지지는 않게 했다. 느리더라도 연결은 살아 있고,
아예 못 쓴다고 판단하면 대화가 통째로 끊긴다.

### 늦게 온 신호가 시각을 되돌리지 않게 했다

`Peer.seenAt` 도 `DeliveryState` 와 같은 문제를 갖는다. 길을 갈아탈 때
먼저 보낸 신호가 나중에 도착할 수 있고, 그러면 "마지막으로 본 시각"이
거꾸로 간다. 더 늦은 시각만 받아들이게 했다.
