# 연결 규약

> 상태: 확정 · 최종 수정 2026-09-17

두 기기가 어떻게 서로를 찾고, 어떤 형식으로 말을 주고받는지 적는다.
이 문서의 형식은 **연결 방식이 달라도 똑같다.** Wi-Fi든 블루투스든 웹이든 같은 봉투를 쓴다.

## 1. 세 갈래 길

| 길 | 속도 | 나를 수 있는 것 | 언제 쓰나 |
|---|---|---|---|
| **A. Wi-Fi** | 수십 Mbps | 전부 (텍스트·음성·영상) | 집에서 준비하고 시험할 때 |
| **B. 블루투스** | 초당 2~5 KB | 텍스트·콕찌르기 | **비행기 안에서. 여기밖에 없다** |
| **C. 웹** | 수십 Mbps | 텍스트 | 아이폰 앱이 만료됐을 때 |

앱은 **A를 먼저 시도하고, 안 되면 B로 내려간다.** C는 사용자가 직접 고른다.

### 1.1 비행기 모드에서는 핫스팟이 안 켜진다

**2026-09-18, 실제 기기(갤럭시)로 확인했다.**

| 해본 것 | 결과 |
|---|---|
| 비행기 모드 켜기 → 핫스팟 | 메뉴가 잠긴다 |
| 비행기 모드 켜기 → **Wi-Fi 를 손으로 켜기** → 핫스팟 | **그래도 잠긴다** |
| 비행기 모드에서 열리는 것 | **블루투스 테더링만** |

블루투스 테더링은 우리에게 쓸모가 없다. 그건 블루투스 위에 IP 망(PAN)을 까는
것인데, **아이폰은 거기 들어가는 화면이 없다.** iOS 는 애플 기기의 개인용
핫스팟에만 블루투스로 붙는다.

그래서 **길 B 가 보조가 아니라 본선이다.** 이 문서의 나머지가 Wi-Fi 를 기본처럼
적고 있는데, 그것은 집에서 준비하고 시험할 때의 이야기다.

**따라오는 결과**

- 비행 중에는 **글·이모지·콕찌르기만** 간다. 사진·음성·영상은 못 보낸다
- 아직 못 해본 것이 하나 남았다: **핫스팟을 먼저 켜고 그 다음에 비행기 모드를
  켜면** 켜져 있던 접속점이 살아남는 기종이 있다. 이게 되면 전부 되살아난다

길이 바뀌어도 대화는 이어진다. 못 보낸 메시지는 쌓아뒀다가 새 길이 열리면 내보낸다.

## 2. 길 A — Wi-Fi

### 2.1 판을 까는 법

```
  안드로이드 폰                          아이폰
 ┌──────────────┐                    ┌──────────────┐
 │ 핫스팟 켜기   │◀── Wi-Fi 접속 ────│ Wi-Fi 목록에서│
 │ (설정에서)    │                    │ 골라서 붙기   │
 │              │                    │              │
 │ 192.168.x.1  │                    │ 192.168.x.20 │
 │  (게이트웨이) │                    │              │
 └──────────────┘                    └──────────────┘
        ▲                                    │
        └────────── 같은 사설망 ──────────────┘
```

핫스팟을 켠 안드로이드가 **항상 게이트웨이**다. 그래서 안드로이드가 **받는 쪽(서버)**, 아이폰이 **거는 쪽(클라이언트)** 을 맡는다. 역할이 고정되면 누가 먼저 말을 걸지 헷갈릴 일이 없다.

셀룰러 신호가 없어도 상관없다. 우리는 인터넷 공유가 아니라 **접속점**만 필요하기 때문이다.

> 앱이 핫스팟을 대신 켜줄 수는 없다. 안드로이드 10부터 막혔다. 앱은 설정 화면을 열어주고, 켜졌는지 확인만 한다. 자세한 사정은 [02-tech-decisions.md](./02-tech-decisions.md)의 D10에 있다.

**붙는 쪽을 대신 붙여줄 수도 없다.** 아이폰에서 지정한 Wi-Fi 에 붙는
`NEHotspotConfiguration` 은 유료 개발자 계정의 권한이 있어야 한다. 무료 서명으로는
쓸 수 없다. 알려주는 데까지가 앱이 할 수 있는 전부다.

### 2.1.1 늘 쓰는 핫스팟을 앱이 알고 있는다

떨어져 앉으면 **"이름이 뭐야"를 물어볼 수 없다.** 그래서 이름과 비밀번호를 앱이
미리 들고 있다가 각자에게 자기가 할 말을 보여준다.

| 역할 | 보여주는 말 |
|---|---|
| 여는 쪽 | 핫스팟 이름을 이걸로 맞춰두세요 |
| 붙는 쪽 | Wi-Fi 목록에서 이걸 고르고 이 비밀번호를 넣으세요 |

값은 `.env` 에 둔다. 저장소가 공개라 코드에 적지 않는다.

```
EXPO_PUBLIC_HOTSPOT_SSID=
EXPO_PUBLIC_HOTSPOT_PASSWORD=
```

`EXPO_PUBLIC_` 값은 **빌드할 때 앱 안에 박힌다.** 바꾸면 다시 빌드해야 하고, 앱
파일을 뜯으면 보인다. 저장소에 안 올라가는 데까지가 여기서 얻는 것이다. 둘만 쓰는
핫스팟이라 거기까지만 한다.

**안 채워도 앱은 돌아간다.** 이름을 알려주는 안내만 빠지고, 상대 화면을 보고
들어가는 예전 방식으로 되돌아간다. 화면에 `undefined` 를 띄우는 것보다 낫다.

### 2.1.2 핫스팟이 꺼진 것을 알아챈다

비행기 모드를 켜면 핫스팟이 같이 꺼진다. **자리에 앉은 뒤 가장 흔한 일이다.**
붙는 쪽은 왜 끊겼는지 알 방법이 없다.

각자의 앱이 스스로 망을 지켜보다가 나온 것을 알아챈다. 이어져 있는 동안은 보지
않는다. 핫스팟이 꺼지면 어차피 끊기므로, 끊겼을 때만 보면서 **왜** 끊겼는지를
알아낸다.

- 여는 쪽 — 그 망의 주인인가로 가른다. 집 Wi-Fi 도 사설망이라 사설망 여부로는
  못 가른다
- 붙는 쪽 — 사설망에 들어와 있나로 본다. 어느 Wi-Fi 인지는 앱이 알 길이 없다

무엇을 보여줄지는 [07-design-system.md](./07-design-system.md) 8장에 있다.

### 2.2 쓰는 번호

| 쓰임 | 번호 | 방식 |
|---|---|---|
| 상대 찾기 | 51703 | UDP |
| 메시지 주고받기 | 51704 | TCP |
| 비상용 웹 채팅 | 51705 | TCP (HTTP) |

### 2.3 상대를 찾는 세 가지 방법

순서대로 시도한다. 하나라도 성공하면 멈춘다.

**방법 1 — 게이트웨이에 바로 걸기 (아이폰이 하는 일, 가장 빠름)**

아이폰은 자기가 붙은 Wi-Fi의 게이트웨이 주소를 안다. 핫스팟을 켠 쪽이 곧 게이트웨이이므로, 거기 51704번으로 바로 걸어본다. 대개 1초 안에 끝난다.

**방법 2 — 소리쳐 부르기 (UDP 브로드캐스트)**

방법 1이 실패하면 사설망 전체에 대고 외친다.

```
보내는 쪽 → 255.255.255.255:51703  그리고  <서브넷 브로드캐스트>:51703
내용: {"app":"skywalkie","v":1,"port":51704,"peer":"<내 식별자>","code":"<여섯자리>"}
```

받은 쪽은 자기 정보를 담아 보낸 쪽 주소로 곧장 답한다. 1초 간격으로 최대 10번 외친다.

일부 기기는 브로드캐스트를 막는다. 그래서 세 번째가 필요하다.

**방법 3 — 훑어보기**

사설망 안의 모든 주소(보통 192.168.x.1 ~ 192.168.x.254)에 동시에 걸어본다. 한 번에 32개씩, 각각 300밀리초만 기다린다. 254개를 전부 보는 데 3초쯤 걸린다.

**전부 실패하면** 잠시 뒤 처음부터 다시 찾는다. 예전에는 여기서 여섯 자리 코드와 주소를 사람이 읽어주게 했는데, 그 기능은 없앴다(7장).

### 2.4 바이트를 메시지로 자르기

TCP는 흐르는 물이라 어디까지가 한 메시지인지 알려주지 않는다. 그래서 길이를 앞에 붙인다.

```
┌──────────────────┬──────────────────────────────┐
│ 길이 4바이트      │ 내용 (JSON, UTF-8)           │
│ (앞이 큰 자리)    │                              │
└──────────────────┴──────────────────────────────┘
```

- 한 메시지의 최대 크기는 1 MB다. 넘으면 연결을 끊는다. 이상한 길이 값으로 메모리를 통째로 잡아먹는 일을 막기 위해서다.
- 길이가 0이면 살아있는지 확인하는 신호(하트비트)다.

### 2.5 처음 만나 인사하기

연결되면 곧바로 서로를 확인한다. 이 절차를 마치기 전에는 아무것도 주고받지 않는다.

```
거는 쪽                                받는 쪽
   │                                      │
   │──── HELLO ──────────────────────────▶│
   │      규약 버전, 내 식별자,            │
   │      내 이름과 캐릭터,                │
   │      내가 마지막으로 받은 순번        │
   │                                      │
   │◀─── HELLO_ACK ───────────────────────│
   │      같은 내용 + 받아들임 여부        │
   │                                      │
   │──── SYNC_REQUEST ───────────────────▶│  (빠진 게 있으면)
   │◀─── SYNC_RESPONSE ───────────────────│
   │                                      │
   │        이제부터 자유롭게 대화          │
```

- **규약 버전이 다르면** 큰 번호끼리는 붙지 않는다. 낮은 쪽에 맞춰 내려간다. 작은 차이면 경고만 띄우고 진행한다.
- **마지막 순번을 서로 알려주는 이유**는 끊긴 동안 놓친 메시지를 바로 알아채기 위해서다. 다시 붙자마자 빠진 것만 골라 받는다.
- 인사가 5초 안에 안 끝나면 연결을 끊고 처음부터 다시 한다.

### 2.6 살아있는지 확인하기

- 5초마다 아무 말이 없으면 길이 0인 신호를 보낸다.
- 15초 동안 상대에게서 아무것도 안 오면 끊긴 것으로 본다.
- 끊기면 1초, 2초, 4초, 8초… 순으로 간격을 늘리며 다시 붙는다. 최대 간격은 30초다.

**사람이 누를 것은 없다.** 핫스팟을 켜고 Wi-Fi 를 고르는 것까지가 사람의 일이고, 서로 찾아 붙는 일은 켜져 있는 동안 앱이 계속한다. "연결" 버튼을 두지 않는 이유다.

간격을 늘리는 이유는 배터리다. 쉬지 않고 두드리면 폰이 먼저 죽고, 그러면 세 시간을 못 버틴다. 그래서 **조건이 갖춰져도 곧바로 안 붙을 수 있다.** 최대 30초까지 기다릴 수 있다.

### 2.7 앱이 뒤로 가면

**뒤로 가면 오래 못 산다. 이건 우리가 어쩔 수 없다.**

| | 뒤로 갔을 때 | 화면이 꺼졌을 때 |
|---|---|---|
| 아이폰 | 몇십 초 안에 잠재운다. 소켓이 끊기고 우리 코드가 아예 안 돈다 | 같다 |
| 안드로이드 | **JS 타이머가 곧바로 멎는다.** 소켓은 살아 있다 | 같다 |

#### 안드로이드는 타이머가 먼저 멎는다

프로세스가 죽어서가 아니다. React Native 가 스스로 끈다.

```kotlin
// JavaTimerManager.kt
override fun onHostPause() {
  isPaused.set(true)
  clearFrameCallback()   // setTimeout/setInterval 을 돌리던 콜백을 뗀다
}
```

그래서 이런 일이 벌어진다.

| | 뒤로 갔을 때 |
|---|---|
| 소켓으로 들어오는 데이터 | **온다.** 네이티브 이벤트라 타이머와 무관하다 |
| 새 말 알림 | **뜬다.** 메시지가 바뀌면 도는 것이지 타이머가 아니다 |
| 5초 심장박동 | **멎는다** |
| 다시 붙기 | **멎는다** |

심장박동이 멎으면 상대가 15초 뒤 "끊겼다" 로 보고 소켓을 닫는다. 다시 붙고 또 15초 뒤 끊기는 일이 되풀이된다. 메시지는 대체로 전달되지만 연결 표시가 계속 깜빡이고 `hello`/`sync` 가 15초마다 오간다.

#### 전경 서비스만으로는 안 된다

전경 서비스는 **프로세스가 안 죽게** 할 뿐이다. 화면이 멈추는 것은 그대로라 타이머도 그대로 멎는다.

되살리는 것은 **헤드리스 작업**이다.

```kotlin
// JavaTimerManager.kt
override fun onHeadlessJsTaskStart(taskId: Int) {
  if (!isRunningTasks.getAndSet(true)) {
    setChoreographerCallback()   // 타이머가 다시 돈다
  }
}
```

그래서 `modules/stay-alive` 는 둘을 겹친다.

```
전경 서비스        프로세스를 안 죽게
  └ HeadlessJsTask  타이머를 살려둠 (아무 일도 안 하고 돌기만 한다)
```

대가는 **알림창에 알림이 하나 떠 있는 것**이다. 안드로이드가 강제한다. 가장 낮은 중요도로 두어 소리도 진동도 내지 않는다.

갈래는 `connectedDevice` 를 쓴다. 하는 일이 정확히 "곁에 있는 다른 기기와 주고받기" 이고, `dataSync` 는 안드로이드 15부터 하루 6시간으로 묶인다.

**아이폰에는 이런 길이 없다.** 아래 두 가지로 메운다.

#### 알림은 두 종류를 구별해야 한다

| | 서버가 필요한가 | 비행기에서 되나 | 우리가 쓰나 |
|---|---|---|---|
| 원격 푸시 (APNs · FCM) | 필요하다 | **안 된다.** 인터넷이 없다 | 안 쓴다 |
| 기기가 스스로 띄우는 알림 | 필요 없다 | **된다** | 쓴다 |

**아이폰도 알림은 잘 된다.** 유료 개발자 계정도 필요 없다. 안 되는 것은 알림이 아니라 **끊긴 걸 알아채는 일**이다. 잠들면 우리 코드가 안 도니 "지금 끊겼네" 하고 띄울 수가 없다.

#### 그래서 이렇게 한다

- **앞으로 돌아오면 곧바로 다시 붙는다** (`useReconnectOnForeground`). 화면을 보는 동안에는 늘 이어져 있게 된다.
- **살아 있는 동안 끊겨 있으면 그 자리에서 알린다** (`useLinkNotifications`). 뒤로 간 직후 몇십 초가 여기에 해당한다.
- **잠든 뒤를 위해 미리 걸어둔다** (`useAwayReminder`). 아래에 따로 적는다.
- 통화 중에는 소리 세션이 앱을 깨워두므로 그동안에는 계속 돈다.

#### 잠든 뒤는 미리 걸어둔 알림이 맡는다

살아 있는 동안 **"10분 뒤에 이걸 띄워줘" 를 운영체제에 맡겨둔다.** 운영체제는 앱이 자든 꺼졌든 약속한 시각에 띄운다. 그리고 1분마다 거둬들이고 다시 건다.

```
도는 중   ─┬─ 걸기(10분 뒤) ─┬─ 거두고 다시 걸기 ─┬─ …   영영 안 뜬다
           1분               2분                 3분

잠듦      ─┬─ 걸기(10분 뒤) ─────────────────────────▶ 뜬다
           마지막으로 돈 때                        10분 뒤
```

**우리가 10분 넘게 멈춰 있을 때만 터진다.** 살아 있으면 계속 거두니까.

10분인 이유는 폰을 잠그면 곧바로 끊기기 때문이다. 2분으로 잡으면 잠글 때마다 운다. 잠깐 딴짓하는 것과 **한참 손을 놓은 것**을 가르는 선이 필요하다.

특히 안드로이드는 **붙은 기기가 없으면 얼마 뒤 핫스팟을 저 혼자 끈다.** 아이폰이 잠들어 클라이언트가 사라지면 그렇게 된다. 그러면 아이폰이 앱을 열어도 못 들어온다. 여는 쪽이 이걸 알아채야 해서 문구도 역할마다 다르다.

글은 "끊겼다" 고 단정하지 않는다. 앱이 잠든 것뿐일 수도 있다. 다만 그동안 말이 안 들어오는 것은 사실이라 **열어보라고 하는 데까지**만 말한다.

#### 아이폰은 소리로 붙든다

아이폰에는 전경 서비스가 없다. 하나 있는 길은 **소리를 내는 것**이다. `audio` 배경 모드를 가진 앱이 실제로 소리를 내고 있으면 iOS 가 안 재운다.

그래서 들리지 않는 소리를 계속 흘린다. 볼륨이 0 이고 담긴 것도 무음이며 `mixWithOthers` 라 **들릴 것도 끊길 것도 없다.** 무음 파일은 규칙이 뻔해서 쓸 때 만든다 — 저장소에 소리 파일을 두지 않는다.

**대가는 배터리다.** 세 시간 내내 소리 장치를 깨워둔다. 폰이 죽으면 대화가 아예 끝나므로 **기본은 꺼둔다.** 연결이 자꾸 끊길 때만 설정에서 켠다.

| | 안드로이드 | 아이폰 |
|---|---|---|
| 붙드는 법 | 전경 서비스 + 헤드리스 작업 | 들리지 않는 소리 |
| 기본값 | 늘 켬 | 꺼둠 (설정) |
| 대가 | 알림창에 알림 하나 | 배터리 |

#### 무엇을 얼마나 기다렸다 알리나

연결은 원래 자주 끊긴다. 화면이 꺼지거나 좌석 사이 벽에 신호가 가리면 몇 초 만에 돌아온다. 그때마다 알리면 **세 시간 내내 폰이 운다.** 그러면 알림을 꺼버리고, 정작 진짜 끊겼을 때 모른다.

| 무슨 일 | 얼마 뒤 | 무엇을 띄우나 |
|---|---|---|
| 우리 망에서 벗어남 | 20초 | 여는 쪽 "핫스팟이 꺼졌어요", 붙는 쪽 "Wi-Fi 에서 나왔어요" |
| 그 밖의 이유 | 90초 | "연결이 끊겼어요. 계속 다시 걸고 있어요" |
| 다시 붙음 | 바로 | "다시 연결됐어요" |

망에서 벗어난 것을 더 빨리 알리는 이유는 **사람이 켜야 풀리기 때문이다.** 다른 이유는 앱이 알아서 다시 붙지만 이건 아무리 기다려도 저절로 안 돌아온다. (`connectPhase.ts` 가 화면에서 같은 판단을 한다)

지키는 것 셋.

- **앱을 보고 있으면 안 띄운다.** 화면에 이미 떠 있다.
- **한 번도 안 붙어봤으면 "끊겼다" 가 아니다.** 첫 연결을 기다리는 중인데 끊겼다고 하면 겁만 준다.
- **끊겼다고 알린 적이 없으면 "다시 연결됐어요" 도 안 띄운다.** 사람은 끊긴 줄도 몰랐다.
- **망 상태를 아직 못 읽었으면 핫스팟 탓으로 몰지 않는다.** 멀쩡한 사람에게 핫스팟을 켜라고 하면 무엇을 눌러야 할지 모른다.

안드로이드에서는 알림 통로를 **메시지와 따로 둔다**(`link`). 메시지 알림을 꺼도 연결 알림은 남아야 한다. 핫스팟이 꺼지면 메시지가 아예 안 오는데, 그때 알림까지 꺼져 있으면 상대가 조용한 것인지 끊긴 것인지 알 길이 없다.

### 2.8 새 말이 왔을 때

| 언제 | 무엇을 하나 |
|---|---|
| 앱을 보고 있을 때 | 화면에 바로 뜬다. 잠금 화면 알림은 안 띄우고 **짧게 한 번 떤다** |
| 앱이 뒤에 있을 때 | 잠금 화면에 띄운다 |
| 앱이 잠들었을 때 | 못 띄운다. 앱을 열면 대화는 그대로 있다 |

보고 있을 때도 떠는 이유는 **다른 곳을 보고 있었을 수 있어서**다. 설정 화면이나 통화 화면에 있으면 새 말이 온 줄 모른다. 다만 대화 화면을 그대로 보고 있으면 거슬릴 수 있어서 **끌 수 있다.**

**보고 있을 때와 안 보고 있을 때를 따로 정한다.** 하나로 묶으면 한쪽을 끄려다 다른 쪽까지 꺼진다. 잠금 화면 알림을 무음으로 두고도 화면을 볼 때는 떨 수 있고, 그 반대도 된다.

설정에서 셋 중에 고른다. 기본은 **진동**이다. 비행기는 시끄러워서 소리는 잘 안 들리고, 상대는 이어폰을 꽂고 있어서 오히려 놀란다. 옆자리 승객도 있다.

| 고른 것 | 안드로이드 | 아이폰 |
|---|---|---|
| 소리 | 소리 + 진동 | 소리 |
| 진동 | 진동만 | 소리 없음 (진동은 기기 설정을 따름) |
| 무음 | 목록에만 쌓임 | 소리 없음 |

**아이폰은 "소리 없이 진동만" 을 앱이 정할 수 없다.** 그래서 아이폰에서는 진동과 무음이 거의 같아진다. 안드로이드는 통로(`channel`)마다 소리·진동이 박혀 있어서 셋을 미리 만들어두고 골라 쓴다 — **한 번 만든 통로는 앱이 못 고친다.** 사용자가 직접 시스템 설정에서 바꾸는 것만 먹힌다.

연결이 끊겼다는 알림은 **이 설정과 상관없이 소리를 낸다.** 그걸 놓치면 말이 아예 안 간다.

#### 저장한 설정은 살아남아야 한다

새 값을 더할 때는 **반드시 `optional` 이나 `default` 로 둔다.** 필수로 두면 예전에 저장해둔 설정이 형식에 안 맞아 통째로 버려지고, `onboardingDone` 까지 날아가서 **비행기 안에서 첫 실행 안내부터 다시 하게 된다.** `settingsSchema.test.ts` 가 이걸 막는다.

## 3. 주고받는 봉투

모든 길에서 똑같이 쓴다.

```ts
{
  v: 1,                    // 규약 버전
  t: "message",            // 종류
  id: "01J...",            // 이 봉투의 고유 번호 (ULID)
  seq: 42,                 // 보낸 쪽 기준 순번
  ts: 1758000000000,       // 보낸 시각
  p: { ... }               // 내용 (종류마다 다름)
}
```

### 봉투의 종류

| 종류 | 무엇 | 답장 필요 |
|---|---|---|
| `hello` | 처음 인사 | `hello_ack` |
| `hello_ack` | 인사 받음 | — |
| `message` | 대화 메시지 | `ack` |
| `ack` | 메시지 받음 | — |
| `read` | 메시지 읽음 | — |
| `typing` | 입력 중 | — |
| `nudge` | 콕 찌르기 | — |
| `reaction` | 메시지에 이모지 붙이기 (2단계) | — |
| `asset_offer` | 사진을 보내겠다는 알림 (2단계) | `asset_request` |
| `asset_request` | 이 조각들을 달라 (2단계) | `asset_chunk` |
| `asset_chunk` | 사진 조각 (2단계) | — |
| `asset_complete` | 다 보냈다 + 검증값 (2단계) | — |
| `presence` | 지금 뭐 듣는지, 배터리 등 | — |
| `flight` | 도착까지 **남은 시간** | — |
| `call_signal` | 통화 협상 정보 | — |
| `sync_request` | 놓친 것 달라 | `sync_response` |
| `sync_response` | 놓친 것 여기 | — |
| `bye` | 나 끊는다 | — |

### `flight` 은 시각이 아니라 남은 시간을 보낸다

도착 **시각**을 보내면 두 폰의 시간대가 다를 때 어긋난다. 비행은 시간대를
넘는 일이 잦고, 아이폰은 기내에서 시간대를 알아서 바꾸기도 한다.

그래서 `flight` 은 `remainingMs` 하나만 담는다. 받은 쪽이 **자기 시계로**
도착 시각을 다시 센다. 오차는 봉투가 건너오는 시간뿐이라 1초를 넘지 않는데,
화면에는 분 단위만 보여주므로 보이지도 않는다.

`remainingMs` 가 0 이면 끈 것이다. 양쪽에서 막대가 치워진다.

### 순번을 쓰는 이유

각자 자기 순번을 1부터 올려가며 붙인다. 받는 쪽은 순번을 보고 세 가지를 판단한다.

- **빠졌나**: 5 다음에 7이 오면 6을 달라고 요청한다.
- **겹쳤나**: 이미 받은 순번이면 버린다. 길을 갈아탈 때 같은 메시지가 두 번 올 수 있다.
- **어긋났나**: 순서가 뒤바뀌어 오면 제자리에 끼워 넣는다.

봉투 번호(ULID)는 순번과 별개로 **전 세계에서 겹치지 않는 값**이다. 내보내고 다시 불러올 때 중복을 판단하는 기준이 이것이다.

### 형식을 믿지 않기

받은 봉투는 전부 `zod`로 검사한다. 통과 못 하면 버리고 기록만 남긴다. 상대가 다른 버전의 앱일 수 있으므로 **모르는 종류가 와도 연결을 끊지 않는다.** 조용히 무시한다.

## 4. 길 B — 블루투스

### 4.1 역할 나누기

블루투스는 **알리는 쪽(주변장치)** 과 **찾는 쪽(중앙장치)** 으로 나뉜다.

| | 역할 | 왜 |
|---|---|---|
| 아이폰 | 알리는 쪽 | 안드로이드 쪽 라이브러리가 알리기를 못 한다 |
| 안드로이드 | 찾는 쪽 | `react-native-ble-plx` 가 찾기만 할 수 있다 |

즉 **고른 것이 아니라 그것밖에 안 돼서** 이렇게 됐다. 그리고 여기서 제약이 하나
따라온다.

### 4.1.1 아이폰 앱이 앞에 있어야 찾힌다

iOS 는 앱이 뒤로 가면 알림에 담긴 서비스 번호를 **숨은 자리로 옮긴다.** 그 자리는
**애플 기기만 읽는다.** 안드로이드는 못 읽는다.

| 아이폰 앱 상태 | 안드로이드가 새로 찾기 | 이미 이어진 연결 |
|---|---|---|
| 앞에 있다 | 된다 | 유지 |
| 뒤에 있다 / 화면 꺼짐 | **안 된다** | **유지된다** |

한 번 이어지면 뒤로 가도 끊기지 않는다. **처음 이을 때와 끊긴 뒤 다시 이을 때만**
아이폰 앱을 앞에 두면 된다. 화면이 이걸 알려줘야 한다
([07-design-system.md](./07-design-system.md) 8장).

**그래서 역할을 바꿨다.** 안드로이드가 알리고 아이폰이 찾는다. 안드로이드는 앞쪽
알림(`connectedDevice`)을 띄운 채 계속 알릴 수 있고, iOS 는 뒤에 있어도 정해둔
서비스 번호로 찾을 수 있다. 찾던 기기를 발견하면 **iOS 가 앱을 깨워준다.**
그래서 BLE 재연결에는 무음 소리로 앱을 붙잡아둘 필요가 없다.

안드로이드용 알리기 모듈을 Kotlin 으로 만들어 붙였다
(`modules/ble-peripheral/android`, `BluetoothLeAdvertiser` + `BluetoothGattServer`).

### 4.1.1.1 엘리베이터로 재봤다 — 2026-09-18

남의 BLE 채팅 앱(bitchat)을 두 폰에 깔고 **비행기 모드 + 블루투스만** 켠 채로
확인했다. 엘리베이터가 좋은 시험 도구였다. 금속 상자라 확실히 끊긴다.

| 한 일 | 결과 |
|---|---|
| 20평 집 끝에서 끝 (벽 하나) | **이어진다** |
| 엘리베이터 탑승 | 끊긴다 |
| 1층 | 끊긴 채 |
| 집 층 복귀, 문 열릴 때 보냄 | 못 간다 (아직 금속 안) |
| 엘리베이터 밖으로 나오자마자 | **간다** |

**저절로 다시 붙었고 몇 초도 안 걸렸다.** bitchat 은 메시라 모든 기기가 알리기와
찾기를 같이 한다. 아이폰이 뒤에 있어도 **안드로이드가 알리는 것을 아이폰이 찾아서**
붙는 길이 살아 있다는 뜻이다. 역할을 바꾼 판단이 맞았다는 실물 근거다.

거리도 비행기 좌석에는 넉넉하다. 다만 비행기는 사람 몸과 좌석이 전파를 먹으니
집보다 나쁘다고 보는 편이 안전하다.

**같이 알게 된 것**: bitchat 은 끊긴 동안 보낸 메시지를 **버린다.** 우리는
저장이 먼저라(`CLAUDE.md`) 남아 있다가 다시 붙으면 나간다. 대비책으로 bitchat 을
쓸 때는 이 차이를 기억해야 한다.

### 4.1.1.2 다음에 해볼 것 — 양쪽 다 알리기

지금은 한쪽만 알리고 한쪽만 찾는다. bitchat 처럼 **둘 다 알리고 둘 다 찾으면**
앞에 떠 있을 때 더 빨리 붙는다. 배터리를 더 쓰는 대신이다.

두 폰 다 알릴 수 있게 됐으므로 이제 할 수 있다. 기본 경로가 실기기에서 도는
것을 본 뒤에 붙인다.

> **만들 때 주의할 점**: 자주 쓰이는 `react-native-ble-plx`는 **찾는 쪽만** 할 수 있다. 알리는 쪽은 만들어진 라이브러리가 마땅치 않아 **아이폰용 네이티브 모듈을 직접 만든다.** CoreBluetooth의 `CBPeripheralManager`를 쓰며 Swift로 200줄 안쪽이다.

### 4.1.2 안 물어보면 조용히 실패한다

안드로이드 12 부터 블루투스로 찾는 일이 위치 정보와 같은 등급이 됐다. 권한을 받지
않고 찾기를 시작하면 **오류도 안 나고 결과만 영영 안 온다.** 화면에는 "상대를 못
찾았다" 로만 보여서 왜 그런지 알 길이 없다.

- `BLUETOOTH_SCAN` · `BLUETOOTH_CONNECT` · `BLUETOOTH_ADVERTISE` 를 **찾기 전에** 묻는다
- 매니페스트의 `BLUETOOTH_SCAN` 에 `neverForLocation` 을 붙인다. 안 붙이면 위치
  권한까지 받고 위치 서비스도 켜져 있어야 한다
- 하나라도 못 받으면 시작하지 않는다. 반쯤 받은 채로 시작하면 위와 똑같이 조용히 실패한다

`src/infrastructure/transport/ble/blePermission.ts` 와 `app.config.ts` 의
`react-native-ble-plx` 플러그인이 이 일을 한다.

### 4.1.3 켜질 때까지 기다리고, 못 찾아도 접지 않는다

두 폰이 영영 못 만나던 원인이었다(2026-09-19).

**아이폰은 무전기를 만든 직후 상태가 "모름" 이다.** 그때 찾기를 시작하면
`react-native-ble-plx`(속은 RxBluetoothKit)가 **즉시 오류로 끝낸다.** 예전에는 그
오류를 "찾기가 안 된다" 로 보고 알리는 쪽으로 돌아섰다. 아이폰의 알리기는 켜지기
전에도 "됐다" 고 답하므로 그대로 굳었고, 결국 **둘 다 알리기만 하고 아무도 안
찾았다.** 안드로이드 쪽 로그에는 알리기가 멀쩡히 찍혀 있어서 안드로이드만 들여다보다
시간을 썼다.

그래서 찾는 쪽은 이렇게 한다.

- **켜진 것을 보고 나서 찾는다.** `onStateChange` 로 `PoweredOn` 을 기다린다. 처음
  쓸 때는 "블루투스를 써도 되나요" 창에 답할 때까지 "모름" 에 머무르므로 넉넉히(60초)
  기다린다
- **꺼져 있거나 권한이 없으면 반대쪽으로 돌아서지 않는다.** 반대쪽도 똑같이 안
  된다. 대신 무엇을 누르면 되는지 적어서 올린다(`not-allowed`)
- **못 찾았다고 접지 않는다.** 20초 찾고 1초 쉬고 다시 찾는다. 상대가 아직 앱을 안
  켰거나 화장실에 갔을 수 있다. 오류가 나면(블루투스가 꺼졌다든가) 1, 2, 4 … 30초로
  점점 길게 쉰다. 안드로이드는 30초에 다섯 번 넘게 찾기를 시작하면 한동안 아무것도
  안 준다
- **끊기면 다시 찾는다.** `onDisconnected` 에서 찾기 고리를 다시 돌린다

`connect()` 가 성공하면 **무전기가 켜진 것**이지 이어진 것이 아니다. 이어지는 것은
`onStateChange` 로 알린다. 그래서 `CompositeTransport` 는 처음에 못 연 길도 계속
지켜보다가 스스로 이어지면 그리로 옮긴다. 옮긴 뒤에는 옛 길의 말을 더 듣지 않는다.
붙는 쪽 Wi-Fi 가 몇 초마다 되뇌는 "찾는 중" 에 블루투스 연결이 "끊김" 으로 바뀌면
말이 안 나간다.

### 4.2 식별자

```
서비스          F7D5061F-298D-46DB-BE86-D1E0C757AB23
보내기 통로      0F52C6B6-FDDA-4E0C-886A-0BB1CA261494   쓰기 (응답 없음)
받기 통로        8966097A-CE16-4B4B-99C4-5DD2409FC9F7   알림
상태 통로        F9F2387C-9014-4C34-AB13-EC01330DB314   읽기 + 알림
제어 통로        57998665-F536-4E22-BBE8-0302580269C6   쓰기
```

### 4.3 긴 메시지 조각내기

한 번에 보낼 수 있는 크기가 작다. 아이폰은 185바이트, 안드로이드는 최대 517바이트까지 늘릴 수 있다. 협상한 값에서 3바이트를 뺀 만큼씩 조각낸다.

```
┌────────┬────────┬────────┬─────────────────┐
│ 묶음번호│ 조각   │ 전체   │ 내용            │
│ 1바이트 │ 1바이트│ 1바이트│ 나머지 전부     │
└────────┴────────┴────────┴─────────────────┘
```

- 한 메시지는 최대 255조각, 즉 약 46 KB까지다. 대개 텍스트라 두세 조각이면 끝난다.
- 내용은 보내기 전에 압축한다. 한국어 텍스트는 절반 이하로 줄어든다.
- 마지막 조각을 받은 뒤 5초 안에 조립이 안 되면 그 묶음을 버린다.

### 4.4 여기선 못 하는 것

- **음성과 영상**: 대역폭이 백분의 일 수준이라 불가능하다. 사용자에게 "지금은 글로만 이야기할 수 있어요"라고 알린다.
- **낙서**: 그림은 크기가 커서 막는다. 대신 "Wi-Fi가 연결되면 보낼게요"라며 대기시킨다.
- **속도**: 초당 2~5 KB다. 긴 글은 몇 초 걸린다. 화면에 보내는 중 표시를 띄운다.

## 5. 길 C — 비상용 웹 채팅

아이폰 앱이 만료됐을 때만 쓴다.

```
  안드로이드 앱                        아이폰 사파리
 ┌──────────────┐                  ┌──────────────┐
 │ 작은 웹 서버  │◀── HTTP ────────│ 192.168.x.1  │
 │ 51705번      │                  │   :51705     │
 │              │                  │              │
 │ 대화 화면을   │──── 실시간 ─────▶│ 글자만 주고  │
 │ 글자로 전달   │   (SSE)          │ 받기         │
 └──────────────┘                  └──────────────┘
```

- 안드로이드 앱이 HTML 한 장과 실시간 통로를 내어준다. 설치가 필요 없다.
- **글자만 된다.** 브라우저는 인터넷 없는 환경에서 마이크와 카메라를 열어주지 않는다. 자세한 사정은 [02-tech-decisions.md](./02-tech-decisions.md)에 적었다.
- 웹에서 주고받은 메시지도 안드로이드 쪽 데이터베이스에 똑같이 저장된다.
- 핫스팟 비밀번호를 아는 사람만 들어온다. 따로 코드를 묻지 않는다(7장).

## 6. 길을 고르고 갈아타기

```
                 ┌─────────────┐
                 │  꺼진 상태   │
                 └──────┬──────┘
                        │ 앱 시작
                        ▼
                 ┌─────────────┐
            ┌───▶│  찾는 중     │◀────┐
            │    └──────┬──────┘     │
            │           │ 찾음        │ 끊김
            │           ▼             │
            │    ┌─────────────┐      │
            │    │  인사 중     │      │
            │    └──────┬──────┘      │
            │           │ 인사 끝      │
            │           ▼             │
            │    ┌─────────────┐      │
            └────│  연결됨      │──────┘
          실패    └──────┬──────┘
                        │ 더 좋은 길 발견
                        ▼
                 ┌─────────────┐
                 │  갈아타는 중 │
                 └─────────────┘
```

### 고르는 기준

점수를 매겨 가장 높은 길을 쓴다.

| 길 | 기본 점수 |
|---|---|
| Wi-Fi | 100 |
| 블루투스 | 40 |
| 웹 | 30 |

연결이 불안정하면 점수를 깎는다. 신호가 약하거나 응답이 느리면 낮은 길로 내려갈 수 있다.

### 갈아탈 때 지키는 것

- **새 길이 완전히 열린 뒤에** 옛 길을 놓는다. 중간에 메시지를 흘리지 않기 위해서다.
- 갈아타는 동안 보낸 메시지는 대기 줄에 쌓인다.
- 새 길이 열리면 인사부터 다시 하고, 순번을 맞춰 놓친 것을 채운다.
- 통화 중에 Wi-Fi가 끊기면 통화는 끝난다. 블루투스로는 이어갈 수 없다. 사용자에게 왜 끊겼는지 알린다.

## 7. 안전

인터넷을 안 타지만 같은 Wi-Fi에 다른 사람이 붙을 수 있다.

- **여섯 자리 코드로 상대를 거르던 기능은 없앴다(2026-09-19).** 두 사람이 쓰는 앱이고, 비행기 안에서 코드를 맞추다 대화를 못 하는 편이 남이 붙는 것보다 훨씬 나쁘다. 붙은 상대는 그냥 우리 둘로 본다. 인사 봉투에 코드가 실려 와도 무시한다.
- 한 번 짝을 맺은 뒤에는 상대 식별자를 기억해서 자동으로 붙는다.
- 내용 암호화는 **1단계에서는 하지 않는다.** 여유가 되면 2단계에서 추가한다(작업 카드 참고).
